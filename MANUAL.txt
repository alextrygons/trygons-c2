1. WHAT THIS PROJECT IS
-------------------------------------------------------------------------------
An autopilot for a boat, running on the Infineon KIT_A2G_TC375_LITE board
(AURIX TC375, three CPU cores). There are two variants:

  * SMALL BOAT (default): outboard engine. The software controls the steering
    motor (no angle sensor: the angle is estimated), the throttle servo and
    the gear servo (Forward / Neutral / Reverse). It uses compass, gyro and
    GPS. Driving modes: MANUAL (joystick), HEADING LOCK and AUTO (waypoint
    program). It navigates without GPS (dead reckoning), calibrates itself
    (TRAINING), limits the engine power until you raise it on purpose, and
    logs everything to an SD card.
  * BIG BOAT: rudder with an angle sensor, heading hold only.

The board has not arrived yet. All of the logic is written and tested in a
PC simulation with a simulated boat. The drivers for the Stage 1 parts
(IMU, GPS, steering motor driver, buttons, end stops, emergency stop, buzzer,
microSD, USB link) are written but not yet tried on the real board; a few
parts are still empty "stubs" (see chapter 17). FIRST_TEST.md is the
checklist for the first power-up and the first steering test.

The three cores:
  core 0  the control loop (20 Hz): modes, steering, engine, PC link
  CPU1    an independent safety monitor (checks core 0 every 1 ms)
  core 2  the logger (writes the SD card)

A PC ground station shows the boat live and sends commands, over the
board's USB cable or to the simulator.

Two kinds of joystick can drive the boat (chosen in the ground station):
the hard-wired analog joystick, or a USB Thrustmaster T.16000M stick +
TWCS throttle, read by a small Teensy 4.1 "bridge" board (chapter 8).

2. WHAT IS IN WHICH FOLDER
-------------------------------------------------------------------------------
  app/            The autopilot itself. Pure C, no hardware code. The same
                  files run on the board and in the PC simulation.
     smallboat.c    small-boat controller: modes, engine, steering, faults
     modes.c        mode manager: the ONLY place that changes the mode
     autopilot.c    steering core (heading hold, outboard angle estimate)
     program.c      AUTO waypoint programs (check, store with checksum)
     powerlim.c     power limit (30 % / 5 % at start, raise / drop)
     servo.c        the ONLY code that writes the throttle servo
     monitor.c      the independent safety monitor (runs on CPU1)
     joystick.c     the joystick, whatever its source (analog or USB)
     joybridge.c    USB joystick: frames from the bridge, fault checks
     joymap.c       joystick source + USB button map (saved with checksum)
     jsframe.c      the bridge frame format (also compiled into the bridge)
     gear.c, throttle.c, nav.c, dr.c, training.c, calib.c
     proto.c, link.c       PC link (frames, telemetry, commands)
     timing.c              CPU time per cycle, overruns
     logq.c, logrec.c, logcore0.c, logfields.h, logger.c   logging
  hal/hal.h       The list of hardware functions the app may use.
  hal/hal_tc375.c The real board versions of those functions.
  hal/hal_pins.h  Every pin of the board in one table (= WIRING.md).
  hal/tc_*.c      The board drivers (UART, SPI, IMU, GPS, ADC, SD card).
  Cpu0_Main.c     core 0: start-up, watchdog, the 20 Hz loop.
                  "#define BOAT_VARIANT_BIG" at the top selects the big boat.
  Cpu1_Main.c     CPU1: the safety monitor loop (1 kHz).
  Cpu2_Main.c     core 2: the logger loop.
  sim/            PC simulation, all tests, simulated boat for the ground
                  station. NOT part of the board build.
  boats/          One file per boat (name + Tailscale address + equipment:
                  generator cap, relays, thrusters; no secrets): the ground
                  station's boat list (chapter 5). Comes with every clone.
  groundstation/  PC ground station and log tools (Python).
  gateway/        gateway PC software (Python; Ubuntu 24.04 / Windows 11): remote access,
                  log copy, cameras, sync. Setup step by step:
                  gateway/README.md.
  bridge/         Teensy 4.1 firmware for the USB joystick (PlatformIO).
                  Setup step by step: bridge/README.md.
  tools/          mapreport.py: memory report from the ADS build.
  WIRING.md       Wiring: joysticks (analog and USB bridge), panel buttons,
                  servos, SD card, USB.
  CLAUDE.md       The project rules (also read by Claude).
  MANUAL.txt      This file.
  Libraries/, Configurations/
                  Generated by AURIX Development Studio. NEVER edit them.

3. WHAT TO INSTALL
-------------------------------------------------------------------------------
Already installed on this PC: everything in this list.
On a new PC, install:

  a) MSYS2 (https://www.msys2.org), which provides gcc and Python. After
     installing, open "MSYS2 UCRT64" from the Start menu and run:

       pacman -S mingw-w64-ucrt-x86_64-gcc
       pacman -S mingw-w64-ucrt-x86_64-python mingw-w64-ucrt-x86_64-tk
       pacman -S mingw-w64-ucrt-x86_64-python-pyserial
       pacman -S mingw-w64-ucrt-x86_64-ffmpeg     (video, recording, tests)

     Then add  C:\msys64\ucrt64\bin  to the Windows PATH (Start -> "Edit
     environment variables" -> Path -> New).
     (Or python.org Python: tick "Add python.exe to PATH", then
      pip install pyserial )

  b) AURIX Development Studio (ADS) from Infineon, for building and flashing
     the board (includes the TASKING compiler and the USB debugger driver).

  c) Git (https://git-scm.com) and VS Code. The project is on GitHub:
       https://github.com/alextrygons/trygons-c2.git

  d) Only for the USB joystick bridge: in VS Code, Extensions -> install
     "PlatformIO IDE". It downloads the Teensy compiler by itself the first
     time you build bridge/ (details: bridge/README.md).

  e) MediaMTX (video relay, for the camera tests and the demo), into
     tools\bin\ of the project (not in git):
       C:\msys64\ucrt64\bin\python.exe tools\get_mediamtx.py
     (The demo asks to do it when it's missing. Check: python
      gateway\toolpaths.py shows where ffmpeg and MediaMTX are.)

  f) Pillow, for the driver screen (see-through panels, outlined text):
       pacman -S mingw-w64-ucrt-x86_64-python-pillow
     (python.org Python: pip install pillow). Without it the driver screen
     still works, only plainer.

  g) The voices for the spoken callouts (Greek + English, offline, about
     130 MB, into tools\bin\piper, not in git):
       C:\msys64\ucrt64\bin\python.exe tools\get_piper.py
     Then restart the ground station. The first start makes all spoken
     sentences once in the background (about 1 minute per language) and
     keeps them in groundstation\sound_cache\. Details: chapter 5D.

  Check in a terminal (VS Code: Terminal -> New Terminal):
       gcc --version
       C:\msys64\ucrt64\bin\python.exe --version

-------------------------------------------------------------------------------

    build_sim.bat

RUN ALL TESTS (before every commit):
    autopilot_sim.exe all
  Ends with  "TOTAL: 144 passed, 0 failed". Takes a few minutes. If anything
  says FAIL, don't commit: find out why first.
    autopilot_sim.exe all --bridge

  USB bridge. Ends with "143 passed, 0 failed, 1 not applicable" (the analog
  calibration test does not apply to the USB joystick).

4A. THE DEMO (ONE CLICK, NO BOAT)
-------------------------------------------------------------------------------
Double-click START_DEMO.bat (project folder) in Windows Explorer. It starts
the whole C2 on this PC, in the Saronic Gulf (37.82 N 23.60 E, between
Piraeus and Aegina):
  * the AURIX simulator (the boat), with the USB joystick as joystick source
  * the gateway (gateway PC software) in PC mode, with MediaMTX
  * 4 camera test streams: FRONT-1, FRONT-2, REAR-LEFT, REAR-RIGHT
  * simulated AIS traffic (10 ships: ferries, cargo, yachts, fishing boats)
  * two ground station windows:
      SHORE (captain)  through the gateway (user captain, password demo),
                       with the DRIVER screen; this is the shore station
      ON BOARD         straight on the simulator: the boat's panel buttons
                       (HDG LOCK, STANDBY, CONFIRM) and the simulated USB
                       joystick (yellow box: lever, stick X, TAKE, AUTO,
                       HDG, STBY)
STOP_DEMO.bat closes all of it. DEMO_SHIP.bat sends a ferry on a collision
course. Everything the demo makes is in demo_run\ (logs in demo_run\logs\,
recordings in demo_run\ssd\); delete that folder any time.

FIRST TIME
  * Python + ffmpeg as in chapter 3 (MSYS2). Missing -> the window says what
    to install.
  * MediaMTX (the video relay): if missing, the window asks to download it
    (about 20 MB, into tools\bin\). Or: python tools\get_mediamtx.py
  * Depth charts: with charts\attica\ (tools\chartprep.py, chapter 9 part K)
    the maps show the real depths. Without them the demo uses a SYNTHETIC
    chart (40 m everywhere, one 2 m shoal 2.9 km SE) - not real depths.
  * The ports 5760-5762, 5790, 8554, 9997, 8080 must be free (no other
    simulator running).

WHAT TO TRY
  1. HDG LOCK with the throttle
       ON BOARD: HDG LOCK (panel). Move the "lever" slider up a little (above
       55 %) -> the boat moves; -1 / +1 change the heading. Lever back to 50,
       STBY or STANDBY -> stop.
  2. A SAVE
       DRIVER screen: the big SAVE button (or a SAVE button on a joystick).
       Screen 2, Cameras tab: "SAVING until ..." and the event in
       demo_run\ssd\video\events\.
  3. A channel switch
       Screen 2, Network tab: channel RF -> MANUAL -> within 60 s KEEP.
       The top line of the driver screen shows the channel. STARLINK is the
       emergency channel: data saver, no sync, a yellow banner.
  4. An AUTO mission
       Screen 2, Program tab: Load file -> demo\demo_mission.json
       (6 waypoints, 6-12 kn) -> Check depth -> Upload to boat. Then Take
       HELM and press the mode button AUTO: the DRIVER screen asks ->
       ACCEPT; then ON BOARD: CONFIRM within 10 s. The boat drives the program (map tab).
       To go faster than 30 %: Raise fwd, type the code, Send code, ON BOARD
       CONFIRM - one step at a time.
  5a. A kayak WITHOUT AIS (only the camera can see it)
       Double-click DEMO_KAYAK.bat while driving (HDG LOCK or AUTO): an
       obstacle 120 m ahead for 40 s. Driver screen / maps: the orange
       sector, OBSTACLE AHEAD + SAVE (STAGE 2). With STAGE 3 switched on
       (Cameras tab, driver ACCEPT) AUTO slows down. The front camera of the
       demo shows a sea video with the AI colours (when the model is
       installed: tools\get_vision_python.py, get_vision_model.py,
       get_vision_samples.py; else only these injected detections).
  5. An AIS collision situation
       While AUTO runs (or in HDG LOCK): double-click DEMO_SHIP.bat. A ferry
       comes from starboard. Screen 2, AIS tab: the ship turns yellow,
       then red (CPA / TCPA). AUTO slows down, then passes astern of the
       ferry (route on the map) and goes back to the leg; the driver screen
       shows the ship line; COLLISION RISK starts a SAVE. In HDG LOCK the
       driver screen PROPOSES a heading: ACCEPT / REJECT.
  6. Remote driving with a USB joystick
       Plug the joystick into this PC. Screen 2, Remote tab: Find
       joysticks, choose it, Take HELM, REQUEST REMOTE DRIVING, then ON BOARD:
       CONFIRM within 10 s. Mode REMOTE MANUAL: the shore joystick drives
       (max 20 % / 5 %). Any move of the ON BOARD stick or lever, or STANDBY,
       takes control back at once; RELEASE ends it.
  7. The joystick always wins
       During AUTO move the ON BOARD stick X slider or press TAKE: MANUAL at
       once, and an automatic SAVE. Resume the program: AUTO resume (captain)
       + ON BOARD CONFIRM.
The REAR and FRONT-2 demo cameras show test pictures (grey, a moving bar, a
time code); FRONT-1 shows a sea video (MaSTr1325 pictures, CC BY 4.0) when
tools\get_vision_samples.py was run.

TWO SCREENS PER STATION (one look: both screens use the same fonts, colours,
buttons and panels - groundstation\theme.py - and switch dark / light together)
  Screen 1 = DRIVING: the full-screen cameras + HUD (chapter 5B). The
             captain sits here (with the joystick): REMOTE MANUAL and
             MANEUVER are started HERE (captain with the manual licence).
             Copilot questions, avoidance proposals and CLEAR SLOWDOWN are

  Screen 2 = NAVIGATION & CONTROL (Greek: "Πλοήγηση & έλεγχος"): the map
             fills the whole window, everything else lies on it in panels.
  Laptop + external monitor: screen 2 stays on the laptop's own (main)

  Size: screen 2 fits from a 1366 x 768 screen up, at 100 - 150 % Windows
  scaling (the panel text gets a little smaller when it must; checked by
  groundstation\test_screen2.py).

CHOOSING THE BOAT (the first line of the top-left STATUS panel)
  The first line of STATUS is the boat dropdown: the boat's name with ▾, a
  lamp next to it and "✓ name verified". Click it: the list of the boats
  folder of the repository (boats\rf49d.json, boats\er69d.json - name +
  Tailscale address, no passwords), every boat by NAME with ONLINE /
  OFFLINE / IP NOT SET / INVALID FILE and its address only as a detail at the end, then
  "Other address ..." and "Disconnect". Choose a boat: user name +
  password, "captain" or "copilot", CONNECT.
  The lamp: green CONNECTED only when this PC found the boat's gateway AND
  is connected to it AND the gateway said the right boat name. Otherwise
  grey with the reason: ONLINE (found, not connected), OFFLINE, IP NOT
  SET, checking ..., "no boat check" (connected to a typed address).
  * The station refuses to connect if the gateway is another boat (each
    gateway knows its own name - gateway config "boat").
  * Then screen 1 opens and a yellow window asks: type the boat's name AND
    tick "I see the LIVE front camera of <boat>" (only possible while the
    front camera picture is live). Only after that the dropdown line shows
    "✓ name verified" and this station can take HELM. "NOT THIS BOAT"
    disconnects.
  * A NEW COMPUTER: clone the repository (chapter 16) - the boats come with
    it; nothing else to copy. A new boat = a new file in boats\ (copy one,
    change id / name / address), commit it.
  * Fill in the real Tailscale IPs: the files have PLACEHOLDER addresses.
  THE BOAT FILE (format 2): "format": 2, id, name, tailscale_ip,
  gateway_port, and the boat's equipment:
    generator_max_pct  the generator's throttle cap in neutral (chapter 7),
                       0 or missing = generator disabled; the AURIX caps it at
                       30 % whatever the file says.
    relays             the relay board's channels (step 6): n (channel),
                       name_el / name_en, type onoff | momentary (a board-timed
                       pulse, max_s <= 5 s) | latching | timed (off after
                       max_s), group engine (IGNITION, STARTER, SHUTOFF: the
                       engine rules) | trim | extra, pair (the other relay of an
                       interlocked pair - must point back, never both on),
                       show_hud (also on screen 1), power_up off | on | keep
                       (engine relays: only off - never switched by themselves),
                       role (engine relays ONLY, required): starter (a
                       momentary relay, max_s <= 5 s) | ignition | shutoff
                       (onoff / latching), each once.
    thrusters          the DP thrusters (chapter 7, DP THRUSTERS): bow / stern:
                       max_pct (0 = not fitted), run_s / rest_s (heat budget:
                       the longest run, the rest after it), jog_m (one JOG
                       step), spot_alarm_m (the off-spot alarm; both DP).
    length_m, draft_m  optional.
  A file without "format" is the old v1: it still loads, with generator
  disabled, no relays and no thrusters. A file that fails the checks (wrong
  type, a pair that is not mutual, a momentary relay longer than 5 s, an
  engine relay with power_up on / keep, an engine relay without its role, an
  engine relay in a pair (SHUTOFF must never be blocked), a STARTER that is
  not momentary, a relay named STARTER / ΜΙΖΑ without the
  role "starter" ...) is listed as INVALID FILE with the reason and is never
  connected: fix the file.
  When this station holds HELM (in STANDBY) it pushes the file's settings to
  the boat (generator cap, the relay table, the DP thruster settings): the
  cap and the thruster settings are RAM only - a boat restart gets them
  again; the relay table is kept in the boat's data flash and a DIFFERENT
  one needs the joystick CONFIRM (chapter 7, RELAY BOARD).
  The event list shows "boat file RF49D: generator max 25 %" and "boat file
  RF49D: DP thrusters, bow 100 %, stern 100 %".
  "Other address ..." (Tools - Connection): the connection box (COM5,
  tcp:..., gw:host:port) for the board on USB, the simulator, the demo and
  service; then there is no boat check.

EDITING ON THE MAP (the copilot's work; the captain can do it too)
  ROUTE      "Edit route": a click on the map adds a waypoint at the end, a
             drag moves one, a right click deletes one; − / + set the speed
             of the new waypoints (while editing: of all of them). "Send
             route" = upload to the boat (refused across shallow water or out
             of the geofence: the leg and the position are shown). Until then
             the panel says NOT SENT (the route is amber on the map).
  MAX SPEED  − / + then "Set": the highest leg speed the boat accepts
             (parameter max_leg_kn).
  GEOFENCE   "Edit fence": clicks add corners (3 .. 50), a drag moves one, a
             right click deletes one; "Send fence" -> the GATEWAY keeps it and
             refuses every route upload / AUTO start that leaves it (code
             120); "Clear fence" removes it. It never steers and never
             changes the throttle. Shown on the map: green = in force, amber
             dashed = being edited / not sent.
  A copilot's route, max speed and geofence (like every driving command)
  wait for the captain's ACCEPT on screen 1 (10 s, else refused): the
  Control panel shows WAITING, then ACCEPTED or REJECTED. The captain's own
  go straight through; single operator = the own confirmation.

Every command gets an answer: OK, or why not (e.g. "JOYSTICK IS IN CONTROL",
"only in STANDBY", "program refused: leg speed out of range (waypoint 3)").
Losing the PC for 3 s gives the alarm "PC LINK LOST" (and drops the power

5D. SOUNDS AND VOICE CALLOUTS

Like a cockpit, the PC speaks. DISPLAY ONLY: the sounds never change the

LEVELS

  CAUTION   one chime + the voice once

6A. FIRST TEST: STEERING ONLY (compile-time switch)
-------------------------------------------------------------------------------
For the first tests on the water the board steers, nothing else. The throttle
and the gear stay with a person at the engine (by hand). Step-by-step
checklist: FIRST_TEST.md.

SWITCH IT ON
  In Cpu0_Main.c remove the comment marks around   #define FIRST_TEST
  build (hammer) and flash. Put the comment back after the first tests.
  It can't be switched on or off from the PC (on purpose).
  FIRST_TEST is ON in git until the first boat tests are done - switch it off
  before testing throttle/gear.

WHAT IS DIFFERENT
  * Throttle and gear outputs are held safe: throttle servo = idle pulse,
    gear servo = neutral pulse, whatever happens (the servos may also be
    disconnected).
  * Power-up needs NO joystick, NO neutral switch and NO gateway.
  * Only STANDBY, TRAINING and HEADING LOCK (plus the BENCH TEST on the
    dock, chapter 6B - it never drives the throttle or the gear). MANUAL
    (joystick), AUTO and remote driving are refused ("not possible in this
    mode").
  * HEADING LOCK and TRAINING steer only while the GPS says the boat moves
    AHEAD (at least 2 kn, course within 60 deg of the heading). Stopped or
    going astern: the steering rests.
  * TRAINING: drive slowly by hand (like its own 20 % throttle, ~4-5 kn).
    Faster, the boat turns too far and TRAINING stops itself.
  * Take over: the STANDBY button or the EMERGENCY STOP (and the person at
    the throttle). Every other safety rule stays active.
  * Shown: a big magenta banner on the ground station "FIRST TEST - STEERING
    ONLY", and in the telemetry (TELEM2 group I).

EMERGENCY STOP (every configuration, not only the first test)
  A mushroom switch that cuts the steering motor / actuator power itself;
  its second contact tells the board (WIRING.md). Pressed: STANDBY at once,
  alarm EMERGENCY STOP, nothing can leave STANDBY until it is released.

-------------------------------------------------------------------------------
6B. BENCH TEST: EVERY SENSOR AND OUTPUT ON THE DOCK
-------------------------------------------------------------------------------
A mode for checking the wiring with the boat on the trailer or tied up,
engine OFF (FIRST_TEST.md part 3). Ground station, tab "Bench".

WHO / WHEN
  * Only the laptop on the USB cable (never through the gateway / from
    shore: "not allowed").
  * Only from STANDBY, not while the GPS says the boat moves (> 1.5 kn), not
    with the emergency stop pressed. Works in the normal and the FIRST TEST
    build.
  * Throttle idle + gear neutral all the time.

WHAT IT DOES
  * Shows every sensor live (10 times a second): IMU (heading, yaw rate,
    roll / pitch, acceleration, compass accuracy 0-3), GPS (fix, satellites,
    SOG / COG, spoofing and jamming states), motor current, limit switches,
    emergency stop, SD card, UART errors.
  * << LEFT / RIGHT >>: the steering motor runs 100, 200 or 300 ms. At most
    one pulse every 0.2 s; never past the estimated maximum angle; refused
    toward an end stop whose switch is open ("at the end stop").
  * Panel buttons: each press is shown (green box + count). They do nothing
    else - except STANDBY, which ends the bench test as always.
  * Buzzer test 1 s.
  * Servo outputs: the throttle and gear pulse widths being sent (idle /
    neutral), to compare with a scope or a servo tester.
  * Monitor trip test (asks first): the CPU1 safety monitor trips for real -
    idle + neutral forced by the monitor itself, steering driver asleep,
    relay open, buzzer, STANDBY, alarm MONITOR TRIP. It stays until the
    board is powered off and on (that is the point: nothing can undo it).

IT ENDS BY ITSELF (back to STANDBY, reason "bench test ended")
  10 min without a bench command, the USB cable unplugged (3 s), HELM taken
  by another station, the boat moving. Also: STANDBY button, emergency stop,
  any fault, the joystick moved (-> MANUAL, normal build).

-------------------------------------------------------------------------------
7. HOW THE BOAT BEHAVES: MODES, BUTTONS, JOYSTICK
-------------------------------------------------------------------------------
MODES
  STANDBY    engine idle, neutral, steering off. Power-up and after faults.
  MANUAL     the joystick: stick left/right = outboard angle (full range),
             forward/back = throttle ahead/astern (centre = idle + neutral).
             Gear changes always go idle -> neutral -> gear, however fast
             you move the stick.
  HDG LOCK   press HDG LOCK on the panel: the autopilot holds the heading
             the boat has now. -1/+1/-10/+10 (panel or PC) change it. The
             throttle stays on the stick (ahead and astern) - you stay in
             HDG LOCK. In reverse the outboard is held straight. Moving the
             stick sideways takes over (MANUAL).
  AUTO       a waypoint program (up to 50 waypoints). Each waypoint has a
             leg speed, an arrival radius and an action: continue / slow
             down / stop in neutral. At the end: stop + alarm (or hold the
             heading slowly). AUTO starts only with the PC "AUTO START"
             AND the joystick CONFIRM within 10 s (stick centred). Pause,
             resume (+ CONFIRM) and skip from the PC. Line following,
             speed control, rough-water slow-down, dead reckoning without
             GPS, GPS integrity check: all as before.
             AUTO RETURN ("Return" in the control panel of screen 2): the
             boat drives the program BACKWARDS from the leg it is on to
             waypoint 1 and stops there in neutral (STANDBY + ARRIVED).
             Each leg back at the speed of that leg, the waypoints keep
             their slow / stop actions. Like AUTO START it needs the
             joystick CONFIRM within 10 s (stick centred; UNCREWED: the
             shore joystick) - from STANDBY, HDG LOCK, MANUAL (stick
             centred) or AUTO itself (running, paused, stopped, finished).
             The copilot may ask for it WITHOUT the captain's ACCEPT (like
             AUTO pause). The gateway checks the way back like a route:
             shallow water (114), the geofence (120); only a program the
             gateway checked itself (uploaded through it) can be driven
             back (121 otherwise: upload it again). The stored program is
             not changed: AUTO START afterwards drives it forward from
             waypoint 1 again; a new upload ends the return. The joystick
             still wins (MANUAL; RESUME + CONFIRM goes on back).
  TRAINING   outboard calibration, started from STANDBY by the PC.

  Mode changes allowed (all others are refused and logged):
     from \ to   STANDBY MANUAL HDG_LOCK AUTO TRAINING REMOTE MANEUVER
     STANDBY        -      yes     yes    yes    yes     yes     yes
     MANUAL        yes      -      yes    yes    no      no      no
     HDG_LOCK      yes     yes      -     yes    no      yes     no
     AUTO          yes     yes     yes     -     no      yes     no
     TRAINING      yes     yes     no     no      -      no      no
     REMOTE        yes     yes     no     no     no       -      yes
     MANEUVER      yes     yes     no     no     no      yes      -
  (REMOTE = REMOTE MANUAL, the shore joystick, chapter 9 part D;
   MANEUVER = steering + gear at idle for the dock / trailer, chapter 7A)
  Extra rules: only the joystick enters MANUAL; MANUAL is left only with
  the stick centred; AUTO needs compass, GPS, a valid program and CONFIRM;
  TRAINING only from STANDBY by the PC; nothing but STANDBY until the
  outputs are armed (chapter 12).

THE JOYSTICK ALWAYS WINS (analog or USB - the rules are the same; the
USB lever has a few extra ones, chapter 8)
  * Take over from ANY mode: stick sideways past 15 % for 0.1 s, forward /
    back (not in HDG LOCK, where that is the throttle), or TAKE. Chirp.
    An AUTO program is suspended (resume later: PC + CONFIRM).
  * Give back: CENTRE the stick, then joystick AUTO (back to HDG LOCK if
    that was interrupted, otherwise STANDBY) or panel HDG LOCK. Not
    centred: refused + chirp. The PC can't take control from the stick.
  * CONFIRM only answers a request from the PC (AUTO start / resume, power
    raise). It counts only with the stick centred and the joystick armed.
    Nothing pending: nothing happens. It never changes the mode by itself.
  * At power-up the stick must be centred, otherwise it is ignored and the
    outputs stay off (alarm) until you let go.
  * Broken wire while it drives: idle, neutral, STANDBY; the gyro holds
    the course until idle + neutral, then the steering stops.

THE STANDBY BUTTON ALWAYS WINS
  Every mode -> STANDBY (idle + neutral first, then steering off). The
  throttle is commanded to IDLE AT ONCE in STANDBY (no rate limit, step 11e;
  normal driving, a lowered power limit and a planned arrival stop come down
  at thr_dn_pc_s, 50 %/s). The gear goes to neutral once the throttle servo
  must be at idle (thr_trav_s, the worst-case 6 s from full). Until idle +
  neutral is reached the boat is still
  steered:
    * from MANUAL: your stick keeps steering the outboard (even if you
      still hold it), then the steering stops;
    * from REMOTE MANUAL: the shore stick is ignored at once, the gyro
      holds the course;
    * from HDG LOCK / AUTO: the heading is held (gyro if the compass is
      gone).
  A stick that is still held can't take control back until it was centred.
  While the stick is held, nothing else can be engaged either: the HDG
  LOCK button is refused (short chirp), AUTO start / resume, remote
  driving and TRAINING are refused with "centre the joystick". Let go of
  the stick (centre), then engage.
  The PC can't override the button. In STANDBY the button acknowledges
  alarms.

AUTO PROGRAM - HOW TO
  1. Program tab: add waypoints (or tick "click adds" and click the map),
     set leg speed, radius, action; choose the end action.
  2. "Upload to boat". The boat checks it (coordinates, number <= 50, leg
     length 10 m .. 50 km, speeds within the maximum, radius 5..500 m) and
     stores it with a checksum (kept after power-off).
  3. Raise the power limit if you want more than ~7 kn (chapter 10).
  4. AUTO START, then CONFIRM on the joystick within 10 s.


-------------------------------------------------------------------------------
7A. CREWED / UNCREWED PROFILE AND MANEUVER
-------------------------------------------------------------------------------
THE PROFILE (decided by the boat, never by a PC)
  CREWED     an onboard joystick (analog, or T.16000M + TWCS through the
             Teensy) was found at power-up and passed its self-check.
             Everything works as in chapter 7: the onboard joystick wins,
             every CONFIRM is pressed on the onboard joystick.
  UNCREWED   no onboard joystick at power-up (or it failed its self-check
             within 6 s). The onboard joystick is ignored completely: no
             MANUAL, no CONFIRM, no joystick buttons; the panel HDG LOCK and
             course buttons do nothing (nobody is on board). Every CONFIRM
             (power raise, AUTO start / resume, REMOTE MANUAL, MANEUVER) is
             pressed on the shore captain's joystick instead: same rules -
             stick centred, within 10 s, only for a pending request.
  Both profiles: the STANDBY button and the emergency stop always work.
  The profile is shown on every screen and in the log.
  It changes only in STANDBY with the boat stopped, and only one way:
  a joystick plugged in on board (and passing its self-check for 10 s)
  makes an UNCREWED boat CREWED. A CREWED boat whose joystick fails or is
  unplugged stays CREWED (that is a JOYSTICK FAULT: idle + neutral,
  STANDBY, alarm). UNCREWED needs a power-up without the joystick. A
  joystick that appears while an UNCREWED boat is driving is a fault:
  STANDBY + alarm PROFILE CHANGED. After every profile change the power
  limit is back at 30 % / 5 % and the outputs re-arm (CREWED: stick centred).

  OPERATING RULE: UNPLUG THE ONBOARD JOYSTICK BEFORE ANY UNCREWED
  OPERATION, and check that every screen shows UNCREWED before the boat
  leaves the dock. With someone on board: joystick plugged in, CREWED.
  The FIRST TEST build (chapter 6A) is always CREWED.

MANEUVER (trailer, ramp, dock approach) - captain only
  * Steering and gear only: the captain's joystick sideways = outboard
    angle, the lever (or stick forward / back) = FORWARD / NEUTRAL /
    REVERSE. The throttle is ALWAYS at idle - no rpm control at all.
  * Gear changes go idle -> neutral -> gear, as always.
  * Start: button MANEUVER (DOCK / TRAILER) on the captain's station (it
    must hold HELM and the user must hold a manual licence), then CONFIRM
    within 10 s (onboard joystick when CREWED, the captain's joystick when
    UNCREWED). From STANDBY or REMOTE MANUAL.
  * Ends: RELEASE, STANDBY button, the onboard joystick (CREWED), any
    fault, HELM lost. Joystick data old / missing: neutral + course held,
    STANDBY after 5 s (as REMOTE MANUAL).
  * Not in the FIRST TEST build.

LOST LINK (UNCREWED ONLY) AND THE ENGINE KILL
  Lost link = no working link to the captain's (HELM) shore station on any
  channel: the gateway dropped the station (no answer for 5 s), the gateway
  itself is lost (3 s), or nobody holds HELM any more (also a RELEASE of
  HELM - hand over with the role swap instead, chapter 9).
  1. Always first: STANDBY - throttle to idle, neutral (fast closing rate),
     alarm LINK LOST.
  2. Near the shore (closer than near_shore_m, default 100 m, to the
     shallow-water / shore data the route check uses) - or the gateway gives
     no valid / fresh shore distance: ENGINE KILL as soon as idle + neutral.
  3. Open sea: wait lostlink_grace_s (default 10 s). Link back in time: the
     boat stays in STANDBY at idle / neutral and the station sees the alarm
     (it never drives on by itself). Otherwise: ENGINE KILL.
  A killed engine stays killed (alarm ENGINE KILLED) until the AURIX is
  POWER CYCLED ON BOARD (a real power-off / power-on; a watchdog reset or a
  software reset of the AURIX keeps the kill) OR the HELM station sends
  RESTART (Tools ->
  Engine; next part: throttle idle, gear in neutral and the e-stop released
  are checked on the boat). A CREWED boat
  never kills the engine: it keeps the behaviour of chapter 9 (REMOTE LINK
  LOST, HELM to nobody, no mode change by itself).
  near_shore_m and lostlink_grace_s are parameters (Config tab) - their
  defaults are still TO CONFIRM. The kill relay itself is not chosen yet
  (WIRING.md 3A): no uncrewed operation before it is fitted and tested.

EMERGENCY SCENARIOS (academy window -> "Emergency scenarios")
  Emergencies on the SIMULATOR of this PC (same inputs as the lessons). A
  scenario first sets up a normal trip (e.g. HDG LOCK at speed), then
  something goes wrong - you are NOT told what to do: react as on the boat.
  Your reaction time is measured from the moment the emergency starts; full
  marks within the scenario's time, fewer points the later you react, failed
  when too late, when you do something dangerous (e.g. a turn to port in
  front of a ship from starboard) or when the boat gets too close to the
  hazard / runs aground. The ten scenarios: compass failure, GPS spoofing,
  slamming, joystick fault, power raise refused, a ship on a collision course
  (AIS), shallow water ahead, a swimmer / kayak near the beach (no AIS!),
  gateway lost, remote link lost. Compass, GPS, slamming, joystick and the
  refusal are REAL faults of the simulated boat (it reacts with its own
  safety rules); the ship, the shallows, the swimmer and the gateway /
  remote-link alarms are drawn by the academy in its small picture of the
  station (map, AIS list, depth, forward camera) - the academy never plays
  the gateway. At the end: the debrief (result, reaction time, closest
  approach, the right action, why) and "Replay" (the recorded track with a
  time slider; the file is kept in academy/data/replays). Results with the
  reaction time go to your logbook.

THE PRACTICAL TEST ON THE BOAT (ground station: menu Academy -> "Practical

  This is the only academy part that sees a real boat - and it only WATCHES
  (the telemetry this station receives + its event log) and grades. It never
  sends anything that drives: every safety rule stays the boat's own.
  CREWED profile only; the examiner (a valid CAPTAIN, his own login + 2FA,
  never the trainee) sits at the station on board.
   1. Examiner logs in; trainee, kind: practical test (one level up), check
      ride (CAPTAIN, every 24 months) or supervised refresher trip.
   2. Type the wind (kn + the direction it comes FROM), tick: calm water,
      examiner on board, the wind is right. "Check" shows everything that is
      missing: test area set (never the placeholder) and the boat inside it,
      STANDBY, start power limit 30 / 5 %, calm water (sea state + slamming
      monitor), wind <= 12 kn and not strong (>= 8 kn) from the north or from
      the right side of the ramp, 08:00-19:00, the exam of the level passed +
      the lessons, fresh telemetry. Then "Start" (the whole ride is recorded in
      academy/data/practical/ and linked to the logbook).
   3. Tasks: leave the harbour, HDG LOCK + a course change of 10 deg,
      joystick takeover + hand-back, the examiner's ALARM (shown on this
      screen only - the trainee must put the boat in STANDBY within 15 s),

   4. Every task approved -> "Final approval": the boat asks for CONFIRM on

      (next login).

CAPTAIN AND COPILOT (the gateway decides, every station shows it)
  CAPTAIN   holds the manual licence and sits at screen 1 (cameras +
            joystick). Holds HELM. The ONLY one who can start REMOTE
            MANUAL or MANEUVER. The captain's own actions go straight to the
            boat.
  COPILOT   everything except manual driving: routes, AUTO, HEADING LOCK
            adjustments, maximum speed, AIS / collision, status - also while
            the captain drives. Every copilot action that changes the
            driving appears on the CAPTAIN'S SCREEN 1 as a question: ACCEPT
            -> sent, REJECT / 10 s / screen 1 closed -> refused. STANDBY,
            HOLD (AUTO pause) and AUTO RETURN never wait (the return still
            needs the joystick CONFIRM on the boat). The copilot can't take HELM
            (code 117) or ask for manual driving (code 118).
  The first licensed user who logs in is the captain; everybody else is a
  copilot (a viewer only watches). A station on the boat can always take
  HELM and then is the captain.
  ROLE SWAP: either side asks, the other one accepts - only if BOTH hold the
  licence. HELM moves to the new captain in one step, so an UNCREWED boat
  never sees a lost link.
  SINGLE-OPERATOR mode (one person, both screens): your own confirmation
  instead of the captain's ACCEPT; manual driving still needs the licence.

GENERATOR MODE (the engine charges the 12 V bank at a fast idle in NEUTRAL)
  This is the ONE thing on the boat that opens the throttle by itself - and
  only in NEUTRAL, only while every condition below holds (checked every
  step, app/generator.c):
    * "GENERATOR AUTO ON" was pressed by the captain (screen 2, control
      panel; a copilot's press is a question on the captain's screen 1).
      It is OFF after every power-up; the STANDBY button switches it OFF
      again (until somebody switches it on).
    * the boat is in STANDBY (not stopping), the outputs are armed, the
      gear is NEUTRAL and the NEUTRAL SWITCH confirms it (a boat without
      the switch never runs the generator), no engine kill, no e-stop, no
      safety-monitor trip, not FIRST TEST, no alarm that is not an
      advisory (acknowledge first - LOW BATTERY is an advisory and does not
      block it), the bank voltage is measured and below gen_start_v 12.1 V.
  What it does: beep + notice GENERATOR STARTING, 10 s later the fast idle
  (gen_idle_pct 8 %), then +2 % every 30 s while the voltage (fast filter)
  still falls, hold when it stops falling (that throttle is remembered in
  the data flash and is the first step next time), -2 % every 30 s when the
  bank rises above 12.5 V. Never above min(gen_max_pct 25 %, 30 %, the power
  limit). Cycle: 20 min, then 1 min at idle and a rest-voltage check: still
  low -> again; recovered -> GENERATOR DONE (notice, auto stays on).
  Every stop is idle FIRST (the throttle comes down at its normal rate and
  nothing opens it again until it is idle): the captain's OFF, the STANDBY
  button, a joystick deflection, any alarm, any mode / gear request (also a
  pending AUTO start waiting for CONFIRM), link lost (UNCREWED), e-stop,
  engine kill, no voltage data.
  GEAR FAULT: the neutral switch opens while it runs, or the boat speeds up
  (SOG + 0.5 kn within 20 s of a throttle rise) -> throttle idle at once
  (the fast STANDBY closing rate), alarm GEAR, generator auto OFF until it
  is switched on again (acknowledge the alarm first).
  CPU1 watches it too: throttle above idle in neutral is allowed only while
  core 0 says "generator active" and at most the generator cap; the gear
  leaving neutral meanwhile = trip (safe outputs, latched).
  Screens: screen 2 status panel row "Generator" + the button; screen 1
  bottom line "GEN x %" while it runs; notices STARTING / FAULT / DONE.
  Parameters (Config tab, STANDBY only): gen_max_pct 0..30 (0 = generator
  disabled; set from the boat file's generator_max_pct when the HELM
  station connects, chapter 5), gen_start_v
  11.5..13 V, gen_idle_pct 3..15 %. Log: event 24 GENERATOR (every state
  change and throttle step), TELEM2 group L.

RELAY BOARD (RS485 Modbus RTU: lights, pumps, trim, engine switches)
  The relays of the boat file (chapter 5) are switched by an 8-16 channel
  Modbus RTU relay board on an RS485 line from the AURIX (hal/tc_modbus.c,
  app/relays.c; board, pins and baud rate TBD: WIRING.md 3D). NO relay is
  in any control path: a relay never changes the mode, the throttle, the
  gear, the steering or a thruster.
  * The relay TABLE (which channel is what) comes from the boat file: the
    HELM station sends it when it connects in STANDBY. The AURIX keeps it in
    its data flash. The same table as the stored one = taken at once. A
    DIFFERENT table is taken only in STANDBY and only after the joystick
    CONFIRM within 10 s (the banner "CONFIRM: RELAY TABLE"; CREWED: the
    onboard joystick, UNCREWED: the shore joystick) - until then the stored
    table stays in use (a wrong boat file must not move the STARTER out of
    the engine rules). No CONFIRM = the station offers it again later.
    While ANY other CONFIRM is waiting (a power raise, AUTO start ...) the
    table is not offered (the AURIX refuses it then): yours goes first. In
    single-operator mode the station asks you first ("send the relay
    table?") - it never confirms by itself.
    Without any table no relay can be switched. A relay channel must exist
    on the fitted board (8-16 channels): a table with a higher channel is
    refused.
  * onoff / latching: on / off. momentary: a pulse timed BY THE BOARD
    (at most max_s, never more than 5 s - it ends even if the AURIX stops).
    timed: on, and switched off by the AURIX after max_s. If a momentary
    relay is still on 0.5 s after its pulse should have ended (the board's
    timer failed), the AURIX switches it OFF itself and keeps trying until
    the readback shows it off. An interlocked
    pair (TRIM UP / TRIM DOWN): never both - the second request is refused
    while the other one is on.
  * Engine relays follow their ROLE (never the type or the name): the
    STARTER is never pulsed by a plain relay command - only the START button
    of the engine page (ENGINE CONTROLS below). IGNITION switches ON only
    with the engine conditions (throttle idle, gear neutral confirmed, e-stop
    released, no ENGINE KILL / monitor trip latched); SHUTOFF ON (= stop the
    engine) is ALWAYS allowed (also while driving, with the e-stop pressed or
    the kill latched: stopping is never refused); OFF always. A SHUTOFF ON the
    relay board can't take yet (silent, or not seen yet in the first second
    after a reset) is kept and sent as soon as the board answers - for 10 s,
    then it is dropped (check the engine: press SHUTOFF again).
  * power_up "on" is applied only ONCE, only with the first table after the
    AURIX's own power-on (never after a watchdog / software reset or a
    reconnect: then the board's states are read back and kept), and it only
    switches ON. Nothing is ever switched OFF by itself; engine relays are
    never switched automatically.
  * The board is read back every 100 ms. No valid reply for 3 s ->
    RELAY BOARD SILENT (an advisory: states shown unknown, no new relay
    command, no buzzer, nothing else changes). It clears by itself when the
    board answers again; an OFF that was waiting is then carried out. With
    no board fitted at all (HAL_RELAY_FITTED 0) there is no such alarm.
  * FIRST TEST: no relay changes at all. A monitor trip / the e-stop leave
    the relays as they are (the board is not a safety path).
  * THE RELAY BOARD ON DRONECAN (step 11f - a BUILD OPTION, hal_pins.h
    RELAY_BUS; the default stays the RS485 board until the board is chosen):
    the relay board can also be the DroneCAN node 30 on the servo bus
    (relays 1-6 = hardpoints 0-5). Every rule above stays exactly the same
    (the AURIX's relay code does not know the bus). What is different:
    - the AURIX sends a new state 10 times at 50 Hz, then nothing (the board
      holds it); after ANY reset of the AURIX it sends nothing until you
      switch a relay - a reset never switches anything.
    - momentary relays (TRIM, the STARTER) are timed by the AURIX: ON
      frames at 50 Hz while the pulse / START hold lasts. If the AURIX stops
      (frozen, reset, cable) the board's own command timeout (<= 300 ms)
      switches the relay off. The STARTER is always also behind the
      hardware time-limit relay (about 6 s: WIRING.md 3D / 3E).
    - readback = the board's hardpoint.Status, if the board sends it. A
      board that does not: the relays panel says "no readback from the relay
      board: the COMMANDED states are shown"; after an AURIX power-on while
      the board kept running the states are unknown until you switch them
      (a relay paired with an unknown, not momentary partner is refused
      until the partner was switched once - switch it OFF first).
    - RELAY BOARD SILENT also when node 30 is not OPERATIONAL, reports
      ERROR, or the CAN bus is down; health WARNING = a notice only. A board
      that loses power or reboots has every relay OFF afterwards; the AURIX
      never switches them back on by itself.
  RELAY BUTTONS (the stations; requests only - the AURIX decides every time)
  * Screen 2: the panel "RELAYS" (collapsible; the station puts it in the
    corner with the most room, never over the boat) shows the boat file's
    relays by group: ENGINE (IGNITION, START (hold), SHUTOFF + RESTART),
    TRIM, EXTRA. An interlocked pair (TRIM UP / TRIM DOWN) is on one line.
    Lit = on, grey = state unknown (board silent, table not active yet):
    a grey button does nothing. onoff / latching / timed: a click switches
    it on / off. momentary "(hold)": press and HOLD - the relay runs while you
    hold it (a board-timed pulse of at most max_s) and goes off when you let
    go. START (hold) = the engine page's START. While the table is not yet
    active on the boat (or waits for the CONFIRM) the panel says so and the
    buttons are grey.
  * Screen 1: the relays with "show_hud": true in a small box left of the
    picture (hidden in MINIMAL). Trim / extra relays are buttons (momentary =
    press and hold); engine relays are only shown there (lamp) - switch them
    on screen 2.
  * Only the HELM station's relay commands are carried out (the AURIX checks
    it). A copilot's ENGINE relay (IGNITION / SHUTOFF) waits for the
    captain's ACCEPT on screen 1; a copilot's TRIM / EXTRA relay goes
    straight. The gateway knows the groups from the relay table the station
    sent (kept on its SSD, state/relay_tables.json); a table it doesn't
    know = every relay waits for the captain's ACCEPT (the station then sends
    the same table once more so the gateway learns it).
  Log: event 25 RELAY (commands, table events, readback changes, board
  lost / back); TELEM2 group M.

ENGINE CONTROLS + REMOTE RESTART (Tools -> Engine)
  The engine page of the HELM station: the boat file's engine switches
  (IGNITION, SHUTOFF: ON / OFF), START (hold) and RESTART. Order: IGNITION
  on -> hold START -> SHUTOFF to stop. The engine kill stays its own AURIX
  output, never a relay.
  * IGNITION ON: the same conditions as below (idle, neutral, e-stop
    released) - refused while you drive. SHUTOFF ON (stop the engine): always,
    no conditions.
  * Every time, on the boat: you hold HELM, the throttle output is idle, the
    gear is in neutral (the neutral switch if fitted, else the gear servo at
    N), the e-stop is released, not the FIRST TEST build. Otherwise refused
    with the reason (shown on the page). NO code, NO joystick CONFIRM, NO
    waiting time, NO limit on the attempts.
  * START (hold): while you hold the button the station sends START 5 times
    a second; each one keeps a 300 ms STARTER pulse on the relay board (timed
    by the board itself). At most 5 s per hold, then 10 s cool-down (also
    after a shorter hold; never past 5 s: with less than 0.1 s of the hold
    left the hold simply ends). The starter stops at once when you let go (or no
    START for 0.3 s), the link / HELM is lost, the e-stop is pressed, the
    gear leaves neutral (also a joystick takeover), the throttle opens, or
    the STANDBY button is pressed. There is no tacho yet: time limit only.
  * RESTART after an ENGINE KILL (lost link, UNCREWED): clears the kill. The
    boat stays in STANDBY at idle / neutral - nothing starts by itself; then
    START the engine. The next lost link kills it again.
  * RESTART after a SAFETY MONITOR trip: the monitor's latch can only go with
    a reset, so the AURIX restarts itself (a software reset, log event 27
    RESTART written first, about 0.5 s later). Everything starts again as
    after power-on: neutral-start interlock, power limit 30 / 5 %, boot
    counter + 1; the relay board keeps its relays (no power_up states). If
    the conditions fail before the reset (e.g. the e-stop is pressed), the
    reset is cancelled.
  * A copilot's RESTART waits for the captain's ACCEPT on screen 1; START is
    the captain's only (gateway code 118). CREWED: the person on board can
    always use the key as well.
  Log: event 27 RESTART (kill cleared / reset / START begins / stops /
  refused, with the reason); TELEM2 group O.

DP THRUSTERS (the thrusters themselves; the DP mode is the next part)
  Dynamic positioning (Minn Kota style) uses two small electric thrusters on
  the 12 V bank: a bow TUNNEL thruster (sideways) and a fixed transom motor
  (fore / aft). This part drives and protects them; only the DP mode below
  ever asks them for thrust - outside DP they ALWAYS stay at 0.
  * The boat file's "thrusters" block (chapter 5) reaches the boat when the
    HELM station holds HELM in STANDBY (RAM only, again after every boat
    restart; TELEM2 group N shows what the boat took). No settings = no
    thruster fitted = never any thrust.
  * Only one part of the software writes them (app/thruster.c): never more
    than the file's max_pct, changes at most 50 %/s, 0 at once on every stop,
    and 0 whenever DP is not active.
  * Heat budget per thruster: running fills it (1 s per s), standing still
    empties it (run_s / rest_s per s). Used up (run_s of running) = that
    thruster stops until it has rested (rest_s), alarm DP THRUSTER HOT; the
    other thruster runs on.
  * The safety monitor (CPU1) knows when DP is active and the caps: thrust
    without DP, or above a cap, trips it, and its safe state puts both
    thrusters to 0 (also with core 0 frozen). The e-stop cuts the thruster
    power with its own contactor and the software sends 0 within one step.
  * Never in the FIRST TEST build, never before the outputs are armed, never
    on the big boat.
  Hardware: WIRING.md 3C (TBD: thrusters, controllers, pins, contactor).
  Log: event 28 DP (settings taken, thruster HOT, cooled down).

DP MODE (SPOT / JOG / CRUISE / TRIP) - the thrusters hold or move the boat
  While DP runs the OUTBOARD stays at idle in NEUTRAL with its steering off
  the whole time (only the generator may open its throttle in neutral, see
  GENERATOR MODE); the two thrusters do everything.
  * SPOT (Spot-Lock): the boat holds the GPS position where DP started and
    the heading it had (the anchor heading). +1 / -1 / +10 / -10 (the panel
    course buttons, or the station's heading buttons) turn the held heading.
  * JOG: moves the spot 1.5 m (boat file jog_m) ahead / astern / to port /
    to starboard of the held heading; back to SPOT once there.
  * CRUISE: holds a heading and a speed over ground on the stern motor
    (0 .. 3 kn, dp_max_kn TO CONFIRM); speed and heading can be changed.
  * TRIP: drives the stored AUTO program at a set speed (at most 3 kn; the
    legs' own speeds still apply); the gateway's speed cap / avoidance
    heading work as in AUTO (also the lost lease: hold the heading, slow,
    DRIVER DECISION); at the last waypoint (or a STOP waypoint) it switches
    to SPOT there. A new program can't be uploaded while a TRIP runs.
  * Start: the HELM station asks (PROTO_T_DP; a copilot's request needs the
    captain's ACCEPT) and the joystick CONFIRM follows within 10 s (CREWED:
    the onboard joystick; UNCREWED: the shore captain's joystick). Only from
    STANDBY (not stopping), outputs armed, GPS trusted, compass working,
    slower than 2 kn, both thrusters set up by the boat file and not hot,
    the outboard at idle (the modelled throttle servo position) and in
    neutral - only a running generator may carry its neutral throttle into
    SPOT. Never in the FIRST TEST build. In DP: SPOT starts at once (it only holds
    the boat where it is); CRUISE / TRIP need the CONFIRM again.
  * The end - the thrusters go to 0 FIRST, then STANDBY:
      DP STOP (a copilot may always send it, without the captain's ACCEPT),
      the STANDBY button, the e-stop, any fault (gear, joystick, monitor ...),
      UNCREWED link lost, GPS lost or suspect (no dead reckoning in DP),
      the compass lost for 10 s (the gyro holds the heading meanwhile; no
      gyro: at once), a thruster HOT (it can't hold with one), pushed more
      than 50 m off the spot or off it for 2 min (TO CONFIRM).
    The onboard joystick (CREWED) ALWAYS wins: deflect it / TAKE = thrusters
    0 at once and MANUAL on the outboard (alarm JOYSTICK, like every
    takeover).
  * Advisories (DP keeps trying, the power limit stays): DP OFF SPOT (pushed
    farther than spot_alarm_m, 15 m, off the spot), DP OVERPOWER (both
    thrusters at their limit for 10 s).
  * Limits of a bow tunnel thruster: it pushes the bow sideways AND turns the
    boat, so it can't move the boat sideways while it holds the heading. The
    heading comes first: in a current or wind from the SIDE the boat slowly
    drifts off the spot (DP OFF SPOT). Turn the bow into the current (+1 /
    +10) - then the stern motor holds it.
  * Generator in DP: it may run while DP holds (SPOT / JOG); a CRUISE / TRIP
    start stops it (idle first). If the stern motor has to push astern hard
    (> 30 % for 5 s) while the boat is still pushed ahead off the spot, the
    gearbox may not be in neutral: GEAR FAULT, the generator idles, auto off,
    DP ends.
  TELEM2 group N (sub-state, spot error ahead / to starboard, held heading,
  speeds, waypoint, why it ended); log event 28 DP (start / sub-state, JOG,
  TRIP end, stop + why).
  On the ground station (step 11):
  * Screen 2, the bottom-left control panel: with both thrusters set up
    (the boat file's thruster settings taken) a line "DP:" with SPOT /
    CRUISE / TRIP and the speed for CRUISE / TRIP (- / +, 0.5 .. 3 kn).
    While a start waits for the joystick CONFIRM the panel says so; DP STOP
    cancels it. In DP the mode buttons and the AUTO rows are replaced by:
    the DP state (sub-state + distance from the spot), DP STOP, the
    generator button; SPOT / CRUISE / TRIP (+ "TRIP: continue" after a STOP
    waypoint) and the speed (SET sends a new CRUISE / TRIP speed); in SPOT /
    JOG the JOG arrows (up = ahead, down = astern, left = port, right =
    starboard; one step = jog_m) and where the spot is ("spot 2.0 m ahead,
    1.5 m to port", red when DP OFF SPOT). The panel's +1 / -1 / +10 / -10
    turn the DP heading. The status panel shows the DP line (sub-state and
    the main number) and the held heading. A copilot's SPOT / CRUISE / TRIP /
    JOG / speed waits for the captain's ACCEPT; DP STOP never waits.
  * Screen 1: the DP box in the CDI place (bottom middle, like MANEUVER):
    the title (sub-state, distance from the spot), the spot vector (the boat
    in the middle with its bow up; the dot = the spot: up = ahead, right =
    starboard; the square's edge = spot_alarm_m) and the thrust bars B (bow,
    sideways) and S (stern, fore / aft) from the middle, -100 .. +100 %;
    amber when a thruster is hot or the boat is off the spot. Display only.
  * The gateway checks a TRIP start like an AUTO start: across or near
    shallow water refused (code 114), out of the geofence refused (120)
    (also "continue": from the DP's next waypoint; the leg from the boat to
    the first waypoint and the geofence as it is NOW are checked). A program
    the gateway has not checked itself - loaded over the USB cable, from the
    boat's memory after a power-up, or before a gateway restart - can't start
    a TRIP (code 121 "route not checked by the gateway"): send the route
    again from screen 2 ("Send route"). In a TRIP the collision
    avoidance works as in AUTO (slow down, route astern, DRIVER DECISION;
    the slowest speed asked in DP is 1 kn); in SPOT / JOG / CRUISE a
    collision danger is the COLLISION RISK + DRIVER DECISION alarm only -
    nothing is steered or slowed, the driver decides (DP STOP, the joystick).
  * Speed on the screens in DP: the boat's dead reckoning takes its speed
    from the outboard (idle in DP), so in DP with the GPS trusted the screens
    and the gateway use the GPS speed / course.

8. THE USB JOYSTICK (THRUSTMASTER T.16000M + TWCS)
-------------------------------------------------------------------------------
WHAT IT IS
  The T.16000M stick steers (left / right = outboard angle). The TWCS
  throttle has a lever that STAYS where you leave it (it has no spring),
  with a NEUTRAL ZONE in the middle (45-55 % of its travel):
      above the neutral zone  = forward      (further = more throttle)
      inside the neutral zone = idle + neutral
      below the neutral zone  = reverse
  Gear changes always go idle -> neutral -> gear, however fast you move it.
  Both plug into a small powered USB hub, the hub into the Teensy bridge,
  the bridge into the AURIX (WIRING.md section 6). If anything in that chain
  fails - a plug, the hub, the Teensy, the wire - the boat sees JOYSTICK
  FAULT within 0.15-0.2 s, exactly like a broken wire on the analog stick:
  if the joystick was driving: throttle idle + neutral, STANDBY, alarm;
  the gyro holds the course until idle + neutral, then the steering stops.

  The T.16000M and the TWCS are NOT waterproof: dry console only.

SWITCH THE BOAT TO THE USB JOYSTICK (once)
  1. Ground station, Joystick tab: Source = "USB bridge", Throttle = "lever".
  2. "Factory default (T.16000M + TWCS)" fills in the default buttons.
  3. Boat in STANDBY -> SAVE TO BOAT. It is stored with a checksum and used
     at every power-up. (Back to the wired joystick the same way.)

DEFAULT BUTTONS (change them with "Map buttons", below)
     TAKE       stick trigger                  (stick button 1)
     STANDBY    stick thumb button             (stick button 2)
     AUTO       TWCS button 1
     CONFIRM    TWCS button 4  (clearly apart from AUTO)
     HDG LOCK   TWCS button 3
     -1 / +1    TWCS hat left / right
     -10 / +10  TWCS hat down / up
     SAVE       stick button 3  (video SAVE on the gateway; optional)
  Which physical button is "TWCS button 1/3/4" depends on the TWCS: check
  with learn mode or the "now" column of the Joystick tab and map them where
  your thumb finds them. The panel STANDBY button stays and always wins.

POWER-UP
  The lever must be IN THE NEUTRAL ZONE and the stick centred. Otherwise:
  alarm "JOYSTICK NOT CENTRED" (= not in neutral), the joystick is ignored
  and the outputs stay off. Put the lever in neutral, let go of the stick.

TAKING OVER (any mode)
  * stick sideways (past 15 % for 0.1 s), or
  * the TAKE button, or
  * moving the lever more than 10 % away from where it was at the last
    hand-back (it was in neutral then, so: leaving the neutral zone).
    In HDG LOCK the lever IS the throttle, so there it does not take over.

THROTTLE PICKUP (no surprise jump)
  When the lever gets the throttle (MANUAL or HDG LOCK entered from STANDBY,
  AUTO or TRAINING), it first does NOTHING. The yellow banner says
  "MOVE THROTTLE TO PICK UP: lever to xx %" and the lever bar shows a yellow
  mark. Move the lever to that mark (within 3 %), or through it, or into the
  neutral zone: from then on the lever drives, starting from the throttle
  the engine has now.
    * Coming from AUTO: the engine keeps its throttle (lowered to the
      30 % power limit that every takeover sets) until you pick it up.
    * Coming from STANDBY: the engine stays at idle + neutral; the pickup
      point is the neutral zone.
  Example: the lever was left at 80 % and you take over: nothing happens
  until you bring the lever to the mark (or neutral).

LEVER AND POWER LIMIT
  Full lever forward = the CURRENT power limit (30 % at start), full lever
  back = the reverse limit (5 % at start). Raising the limit never makes the
  boat speed up by itself: if the lever is fully forward when you raise from
  30 to 50 %, the throttle stays at 30 %. Pull the lever back a little and
  push it forward again - now full lever is 50 %.

HAND-BACK
  Stick centred AND lever in the neutral zone, then AUTO (or panel HDG
  LOCK). Otherwise refused + chirp. (This means the engine is at idle when
  you hand back.)

CONFIRM (power raise, AUTO start / resume) on the USB button follows the
  same rules as before: only with the stick centred and the joystick armed,
  only for a pending PC request. The lever position does not matter here.

MAP BUTTONS (ground station, Joystick tab, boat in STANDBY)
  1. "Map buttons (guided)". Let go of everything, click Next.
  2. Move the stick fully right, hold, Next (steering axis found).
  3. Push the lever fully forward, hold, Next (throttle axis + direction).
  4. For each function press the button you want. A button already used
     for another function is refused at once ("already TAKE - press a
     different button"). TAKE, AUTO and CONFIRM must be mapped; the others
     can be skipped.
  5. SAVE TO BOAT. The boat checks again: TAKE, AUTO and CONFIRM on the same
     button -> refused ("two functions share a button").
  Note: the buttons keep their OLD job while you map them - pressing the
  TAKE button switches to MANUAL. That is on purpose (the joystick is never
  switched off). Press the panel STANDBY before saving.
  One function only: the "Map" button in its row.

LEARN MODE (on the Teensy, to see what is what)
  Teensy on the PC USB, VS Code -> PlatformIO -> Monitor, type  l  + Enter.
  Every button / hat / axis you move is printed with its code number.
  While learn mode is on the boat keeps the USB joystick disarmed.
  Other joysticks than the Thrustmaster: calibrate first ( c ), see
  bridge/README.md.

STATUS TO WATCH (Joystick strip / tab)
  "USB bridge: 100 frames/s, CRC errors 0, stick OK, throttle OK" is normal.
  Fewer frames/s, growing CRC errors: bad wire / interference. More than 5
  CRC errors per second, a frozen counter, an unplugged device, an invalid
  axis or no frame for 0.15 s = JOYSTICK FAULT (the reason is shown).
  For the first 5 s after power-up the bridge may still be starting (USB):
  no alarm then, the joystick is just not armed yet.

MEASURED IN THE SIMULATION (bridge + hub modelled)
  TAKE pressed -> mode change on the AURIX: average 34 ms, worst 60 ms
  (200 presses; target < 100 ms). Worst case by design: USB + hub 2 ms +
  frame period 10 ms + UART 3 ms + control loop 50 ms = 65 ms.

9. THE GATEWAY (GATEWAY PC) AND REMOTE ACCESS
-------------------------------------------------------------------------------
THE IDEA
  The gateway PC on the boat (a Lenovo ThinkPad L390 Yoga with Ubuntu 24.04
  LTS or Windows 11) is the only way in from the internet. The
  AURIX is NEVER on the network: it talks only to the gateway PC, over a cable
  (UART, the same frames with checksum as the USB laptop link). The gateway PC sits
  on the boat LAN behind the Teltonika router; shore PCs and the iPhone
  reach it only through a VPN (Tailscale) that the boat opens itself -
  no open ports, works behind the 4G operator's CGNAT.
  The USB laptop, the onboard joystick and the STANDBY button work exactly
  as before, with or without the gateway PC.
  Setup step by step: gateway\README.md.
  The gateway PC: Ubuntu 24.04 LTS is recommended at sea (no forced updates or
  restarts); Windows 11 works too (Windows Update set to "ask, never restart").
  It starts by itself at boot and restarts after a crash (Ubuntu: a systemd
  service; Windows: the Task Scheduler task "Trygons Gateway"). Power: a 12 V
  -> USB-C PD car charger from the bank; its own battery is the UPS (charge
  limit 80 %: TLP / Lenovo Vantage); it keeps running with the lid closed.
  Ethernet to the router and to the camera PoE switch (USB-Ethernet adapters
  if it has no RJ45). The AIS receiver is a USB one. The serial devices are
  named in gateway.json by a stable id (python gateway.py --list-serial).

A. THE GATEWAY LINK (AURIX <-> gateway PC)
  * UART 921600 baud (AURIX ASCLIN1: P15.0 -> adapter RXD, P15.1 <- adapter TXD)
    through a 3.3 V TTL USB-UART adapter (FTDI / CP2102 at 3.3 V) on the
    gateway PC. NEVER an RS232 port or cable: its +-12 V destroys the AURIX
    pins (WIRING.md section 7).
  * The AURIX sends the gateway PC: telemetry, and a COMPLETE COPY of its log (every
    record it writes to its SD card, numbered). The gateway PC writes it to its
    SSD as .TLG files (aurix_logs\YYYYMMDD\P<boot>_<file>.TLG) - readable with
    logview.py / log2csv.py like the SD card files.
  * If the cable is too slow at some moment, the AURIX drops records for the
    gateway PC FIRST - never control traffic. The gateway PC notes the missing numbers in
    gaps.csv. The AURIX SD card is always complete: it stays the independent
    black box.
  * The gateway PC sends a status once a second (its "I'm alive"). Silent for 3 s:
    alarm GATEWAY LOST. Nothing else changes (no mode change) - unless you
    are driving remotely (part D).
  * The gateway PC's SSD missing / failing: alarm GATEWAY STORAGE; everything else
    keeps running. The data are on the gateway PC's own SSD.
  * TIME: the AURIX sends GPS time to the gateway PC once a second; the gateway PC sets its
    clock from it, so the boat log, the gateway logs and the video all have
    the same time.
  * Ground station, System tab: "gateway: OK / LOST, gateway log copy up to
    record N, gaps".

B. USERS, ROLES AND HELM
  * Every station logs in to the gateway (user + password, or a key).
    VIEWER = watch only. HELM = may hold HELM.
  * Only ONE station holds HELM; only its commands are carried out (the
    AURIX checks it; others get "NOT HELM"). The top bar of the ground
    station shows "HELM: YOU - ..." or who has it; buttons "Take HELM" /
    "Release".
  * A station ON THE BOAT (USB laptop, boat LAN) can always take HELM, also
    from a remote one. A remote station only when nobody has it. The USB
    laptop takes a free HELM by itself.
  * The onboard joystick and the STANDBY button still beat everything.
    Power raise, AUTO start / resume and remote driving still need the
    joystick CONFIRM on the boat - remote can never do them alone.
  * Every command carries station, number and time; the gateway refuses
    duplicates, old ones (more than 2 s), out-of-order and too many. A PC
    with a wrong clock is fine (the gateway measures the difference).
  * Slow or far links get reduced telemetry (2 times a second, the
    essentials) automatically; the System tab shows every station's
    latency.
  * Remote HELM station lost: alarm REMOTE LINK LOST, HELM back to nobody,
    no mode change (remote driving: part D).
  * TRUST: which station is "on the boat" is decided by the gateway PC (where it
    connects from); the AURIX can't check it. A faulty or hacked gateway PC could
    therefore claim to be a station on the boat. What it still can't do:
    leave MANUAL against the joystick, override STANDBY, start AUTO /
    remote driving or raise the power without the joystick CONFIRM on
    board, steer outside AUTO, or go faster than the power limit.
  * iPhone: http://trygons-gw:8080 over the VPN, view only (HELM from the
    web page only if switched on in the gateway config).
  * Audit log on the gateway PC: who connected, who held HELM, every command and
    its answer. Security rules: gateway\README.md section 12 - please do
    all of them (change ALL default passwords, VPN only, cameras without
    internet, separate networks).
  * Connect the ground station through the gateway:
      python app.py gw:trygons-gw:5761     (asks for user + password)

C. INTERNET CHANNELS (router Teltonika RUT901)
  Channels: 4G (SIM 1), 4G SIM 2, RF (future), STARLINK.
  STARLINK = EMERGENCY ONLY: metered, never used for sync, and in AUTO
  only when every other channel is down.
  The RUT901 has two SIM slots but one modem: only one SIM works at a time
  (switching takes 30-90 s; SIM 2 shows "standby").

  Ground station, Network tab: every channel with up/down, internet,
  latency, loss, signal (4G), data used today / this month; the active one
  marked ">". Buttons:
    AUTO           failover by priority (4G, 4G SIM 2, RF); STARLINK only when
                   all are down; back to a normal channel when it has been
                   stable for 60 s.
    MANUAL <ch>    use this channel; if it has no internet for 30 s ->
                   the next working one + alarm CHANNEL FALLBACK; back when
                   it is stable again. STARLINK asks "EMERGENCY LINK -
                   metered data" first. The fallback is STARLINK only if no
                   normal channel works (your chosen one included).
    MANUAL STRICT  only this channel, never switch. Only from a station on
                   the boat, with a warning.
    KEEP           every switch you ask for is a TRIAL: press KEEP within
                   60 s (over the new link). If you can't (the new link is
                   dead), the gateway goes back to what worked - you can
                   never lock yourself out from shore. It goes back to
                   STARLINK only if you had chosen STARLINK yourself;
                   otherwise it picks again (a normal channel first).
  Only the HELM station or a station on the boat may change the channel.

  While STARLINK is active: big "STARLINK - EMERGENCY LINK" banner, data
  saver ON (reduced telemetry, cameras front only, low - part E), sync
  stopped (part G), data counter for this session and the month, warning
  at the monthly limit you set (gateway.json, monthly_warn_gb, 20 GB).

  Setup of the RUT901 and Starlink: gateway\README.md section 13 (LAN
  range 10.42.0.x FIRST, then Starlink in bypass mode on the WAN port,
  failover with health checks, SSH key for the gateway PC).

D. REMOTE JOYSTICK DRIVING FROM A SHORE PC (mode REMOTE MANUAL)
  RULE: somebody is ALWAYS on board while the boat is driven remotely.
  Priority, always: STANDBY button > onboard joystick > remote joystick >
  autopilot modes.

  On the shore PC: plug in a USB joystick (e.g. T.16000M + TWCS; any
  standard joystick works). Ground station connected through the gateway
  (gw:...), Remote tab:
    1. "Find joysticks" shows the devices with their numbers. Choose the
       device + axis for steering and for the throttle, "invert" if it goes
       the wrong way, "lever" for the TWCS. Save.
    2. Take HELM. Tick "send my joystick (30 Hz)".
    3. REQUEST REMOTE DRIVING. The boat shows "PRESS JOYSTICK CONFIRM -
       REMOTE DRIVING": the person ON BOARD presses CONFIRM within 10 s.
       The mode becomes REMOTE MANUAL (blue).
    4. Drive: stick X = outboard angle (rate-limited, 20 deg/s), lever =
       throttle with the neutral zone and THROTTLE PICKUP like on board
       (chapter 8). Maximum 20 % forward / 5 % reverse (and never above the
       power limit). Slamming reduction applies (part H).
    5. RELEASE when done (-> STANDBY: idle, neutral, steering off).
  STANDBY button while driving remotely: the shore stick is ignored at
  once; the gyro holds the course until idle + neutral, then steering off.
  It also ends when: the onboard joystick moves or TAKE is pressed
  (-> MANUAL at once), STANDBY is pressed, any fault, a station on board
  takes HELM, the remote driver's link fails.

  LINK PROBLEMS: joystick data older than 0.3 s, a gap of 0.3 s, or a link
  latency over 0.4 s -> at once: throttle to idle, neutral, the outboard
  holds the heading on the gyro, alarm REMOTE DRIVING LINK LOST. After 5 s
  without the link: STANDBY. It NEVER starts again by itself - the request
  + CONFIRM on board is needed again.
  The joystick packets travel by UDP (signed with a key the gateway gives
  at login): a lost packet is simply replaced by the next one 33 ms later.
  (By TCP, one lost packet would hold everything for 0.2-0.6 s and the boat
  would declare LINK LOST every few seconds on 4G.)
  Measured in the simulation (4G, ~80 ms round trip, 1 % packet loss):
  stick move on shore -> visible in the boat's telemetry: median ~185 ms,
  max ~230 ms; 60 s of driving without a single LINK LOST.

E. CAMERAS (4 x TP-Link Tapo C310)
  FRONT-1 (main), FRONT-2 (backup), REAR-LEFT, REAR-RIGHT. Cable (Ethernet),
  on their own camera network behind the gateway PC; they have NO internet (the
  cloud is not used). The gateway PC relays the video (MediaMTX, no re-encoding).
  Video is never needed for safety: a camera problem never changes the mode.

  Ground station, Cameras tab (the big driver screen comes in part I):
    Full          front HIGH, mirrors LOW
    Front only    front LOW, mirrors off
    Mirrors only  rear cameras LOW
    All off       no video (no data used)
  Only what you asked for is sent over the internet. On STARLINK (or with
  data saver) only the front camera LOW is allowed - "override" works with
  data saver on 4G, never on STARLINK. Per camera: state (OK / FROZEN /
  DOWN), bitrate in and out, total.
  FRONT-1 frozen or gone (no new picture for 1 s) -> the front view switches
  to FRONT-2 by itself ("FRONT-1 LOST - showing FRONT-2"), and back when
  FRONT-1 has worked again for 2 s. A frozen picture always shows
  VIDEO FROZEN within 1 s. Remote driving warns if no front camera is live.
  Measured in the simulation: about 135 ms on the boat LAN, ~190 ms over 4G
  (plus the camera's own delay, about 0.3-1 s for a Tapo - not measured).
  Camera setup, firmware updates (the "Camera internet 30 min" button,
  only from a station on board), wiring: gateway\README.md section 14,
  WIRING.md section 8.

F. VIDEO RECORDING: RING BUFFER AND SAVE
  The gateway PC records all 4 cameras (full quality) all the time, in 1-minute
  files on its SSD. Only the last 5 / 10 / 20 / 30 / 60 minutes are kept
  (the "ring buffer"; Cameras tab -> ring buffer, HELM or a station on board).
  Recording never uses the internet and never affects driving.

  SAVE keeps the whole ring window before it + 2 minutes after it (all
  cameras), with: time, position, speed, heading, mode, alarms, what
  triggered it, and the name of the AURIX log file (record number) of that
  moment. A SAVE starts by:
    * the SAVE button (Cameras tab; the big driver screen in part I),
    * the SAVE button on the boat's USB joystick (default: stick button 3;
      "Map buttons" in the Joystick tab) or on the shore PC's joystick
      (shore_joystick.json "save_button", default button 3),
    * automatically: a new alarm (not "arrived"), a fault, the joystick
      taking over from HDG LOCK / AUTO / REMOTE / TRAINING, STANDBY because
      of a fault, slamming over the red limit (part H).
  Several triggers close together are one SAVE (it gets longer). VIEWERs
  can't SAVE.
  Where: <SSD>\video\events\YYYYMMDD-HHMMSS_<trigger>\<CAMERA>\*.ts and
  event.json. The files play in VLC.
  Watch it next to the log: python logview.py -> "Open event..." (choose
  event.json: video + its log, cursor at the trigger) or "Video folder...";
  choose the camera, click in the plots or press Play. Accuracy about 1 s.

  SSD space (1 hour of video from 4 Tapo C310 at full quality is about
  3-4 GB, 4 x ~2 Mbit/s - check "GB/h" in the Cameras tab with the real
  cameras): when the SSD runs low the gateway PC deletes, in this order:
    1. the oldest ring buffer files,
    2. the oldest SAVEs that are already copied to the shore PC (part G),
  but NEVER a SAVE that is not on the shore PC yet. If that is not enough:
  STORAGE FULL (alarm GATEWAY STORAGE on the boat): new SAVEs are refused,
  the ring buffer keeps running. Free space: sync to the shore PC, or copy
  the events away and delete them.
  A camera that stops recording (cable, power) is restarted every few
  seconds; the others keep recording. "not recording: ..." shows it.

G. SYNC TO THE SHORE PC
  The gateway PC copies its SSD to the shore PC by itself, over the VPN, whenever
  the boat is on 4G / 4G SIM 2 / RF (NEVER on STARLINK). In this order:
    1. black box / alarms   AURIX logs with an alarm, fault or SAVE in them,
                            and every SAVE's description (event.json)
    2. event logs           the audit log (who did what), log gaps
    3. telemetry logs       all other AURIX logs
    4. saved events         the SAVE video
    5. ring video           only if switched on (recording.ring_sync) - OFF
  * It only uses spare bandwidth: it measures its own ping to the shore and
    slows down at once when the link starts to queue (video, telemetry and
    commands stay fast). During REMOTE MANUAL it stops completely.
  * A broken connection continues where it stopped (checked with SHA-256).
  * A file counts as "synced" only after the shore PC has checked it. Sync
    never deletes anything; only when the SSD runs low does the gateway PC delete
    SYNCED data (part F).
  Network tab: SYNC state, speed, ping, what is waiting per class, the last
  confirmed file; on the shore PC also what it has received.
  The files arrive on the shore PC in <folder>\trygons-c2\ (same layout:
  aurix_logs, audit, video\events) - open them with logview.py.
  Setup: gateway\README.md section 16.

H. SLAMMING (hull impacts) AND AUTOMATIC THROTTLE REDUCTION
  A BNO085 motion sensor measures the vertical acceleration about 200 times
  a second. Shown and logged: the hardest impact (g), impacts per minute,
  and the "level" (running average of the impacts; it falls again when the
  water gets smooth).
    CALM     nothing happens
    YELLOW   level above 70 % of the limit: warning beep; the forward
             throttle is reduced one step (10 %) at once and again every 5 s
             while it stays yellow (never below 30 %)
    RED      one impact harder than the limit (default 3.0 g): red alarm
             SLAMMING, one more step down at once, and a video SAVE.
             The power limit STAYS (setting slam_red_reset = 0, "STEP",
             the default): a sudden drop to 30 % can be dangerous in a
             following sea (a wave from behind). slam_red_reset = 1
             ("LIMIT_RESET") brings back the old behaviour: the power
             limit also drops to 30 %, like for every other alarm.
  It only ever REDUCES the throttle, in every mode (MANUAL, HDG LOCK, AUTO,
  REMOTE). The throttle comes down at its normal rate. After 30 s of calm
  water the reduction goes back slowly (+5 % every 10 s). In AUTO, slamming
  also counts as rough water (the boat slows its target speed, chapter 7).
  OVERRIDE (only with the joystick on board, never the remote driver):
  "kick-down" - ease the throttle off (below 85 %), then push it to full
  and hold 1 s. The reduction is lifted (warning beep, "OVERRIDE" shown)
  until you go below the reduced value again. The power limit still applies.
  Staying at full throttle all the time never overrides.
  The limit: parameter slam_limit_g (1-8 g); the RED action: parameter
  slam_red_reset (0 = STEP, 1 = LIMIT_RESET). The captain proposes, the
  driver confirms on the driver screen (part I).
  Sensor not working: "slamming sensor lost" warning, no reduction, the
  boat drives on normally.
  In the log: every impact as a SLAM event (peak, level, rate, reduction).

J. AIS: OTHER SHIPS (RECEIVE ONLY)
  The gateway PC listens to AIS (no transponder: other ships do NOT see us on AIS).
  Receiver: a USB AIS receiver on the gateway PC with its own
  VHF/AIS antenna. The AURIX never sees AIS - the gateway PC decodes it:
    * position reports Class A (big ships) and Class B (small craft),
    * name, size, type, destination (static data).
  Each ship shows its age; with no new position it becomes STALE after
  3 min (Class A) / 6 min (Class B) and disappears after 15 min. Between
  reports the position is predicted from speed and course. Wrong data is
  ignored (bad checksum, impossible jumps).
  AIS RECEIVER SILENT (alarm, warning only): no AIS message for 5 minutes
  while at sea (moving or in a driving mode). Check the antenna cable and
  the receiver. It never changes the mode or the power limit.
  ONLINE AIS (AISHub, wider area): OFF by default; only on 4G / RF, NEVER
  on STARLINK. Ships seen by our own receiver keep our data when it is
  newer.
  SECOND GPS: if the AIS device has its own GPS (a future Class B
  transponder, or $GPRMC from the receiver), the gateway PC can send it to the
  AURIX as a second, independent GPS: setting ais.second_gps = true on the
  gateway PC AND parameter gps2_check_m (e.g. 30) on the boat. A main GPS more than
  that far from the second one is not trusted (spoofing). Tested: drags of
  0.2 m/s and slower are NOT found by the other checks within 10 minutes,
  the second GPS finds them at 30 m. Both OFF by default.
  GPS TRUSTED AGAIN AFTER A SPOOF: 60 good fixes in a row (1 per second)
  that agree with dead reckoning. At speed the dead reckoning speed can be
  off (e.g. 15 % with fouling or a head sea, no paddlewheel); then:
    * with the second GPS switched on, or with a paddlewheel: the GPS may
      differ from dead reckoning ALONG the course by DR's speed error ->
      trusted again after about 60 s;
    * with neither: only when GPS and dead reckoning agree - this can take
      several minutes at speed (AUTO goes on by dead reckoning, slower,
      and holds the heading at the DR limit). It can't safely be faster:
      a spoofer dragging the position slowly along the course looks
      exactly like a wrong speed estimate.
  Across the course nothing is relaxed: a GPS pulled sideways is never
  trusted again.
  AIS DOES NOT SHOW small boats, jet skis, swimmers, kayaks or anything
  without a transponder. The lookout on board and the cameras stay essential.

L. SHALLOW WATER
  Limit = the larger of 3.0 m and (draft + margin). SET THEM ON THE GATEWAY PC
  (gateway.json "shallow"): draft_m = from the water line to
  the lowest point of the outboard with the leg DOWN (measure it!), margin_m
  = how much water you want under it (1 m), shallow_m = at least this (3 m).
  The ground station shows the limit (Program tab profile, red line).
  AUTO PROGRAMS (Program tab):
    * "Check depth": every leg must stay over water deeper than the limit
      and not pass closer than 50 m to shallower water. A bad leg is shown:
      the message gives the leg and the position, a red X on the map, the
      depth profile (red = too shallow).
    * Upload and AUTO start / resume through the gateway are REFUSED the same
      way by the gateway PC ("shallow water on the route: leg ... at lat lon"), also
      the leg from the boat to the waypoint at AUTO start. Without charts on
      the gateway PC AUTO is refused ("no depth charts").
  WHILE DRIVING (any mode): if the boat will be over shallow water within
  the next 30 s (at least 200 m ahead) -> "SHALLOW WATER AHEAD" on both
  screens. In AUTO the boat also slows to 4 kn and the SHALLOW WATER alarm
  sounds. In MANUAL / HDG LOCK / REMOTE it is a warning only: you steer.
  Every collision-avoidance route (part M) passes the same depth check.
  The charts are free data and NOT FOR NAVIGATION: near the coast, in
  harbours and where there is no data, "no data" counts as shallow.
  How AUTO is slowed: the gateway PC sends a "navigation request" twice a second
  (speed cap, avoidance heading, alarms) that the boat applies only in AUTO.
  If the gateway PC goes quiet in the middle of such a request, the boat holds its
  heading, slows to 4 kn (parameter nav_lost_kn) and sounds COLLISION RISK -
  DRIVER DECISION. Joystick and STANDBY always win.

M. COLLISION AVOIDANCE (AIS SHIPS)
  AIS DOES NOT SHOW small boats, jet skis, swimmers, kayaks, divers or
  anything without a transponder, and a ship's AIS can be wrong, late or
  switched off. Collision avoidance helps with BIG ships only. KEEP A
  LOOKOUT. A radar reflector on the boat helps big ships see YOU.
  The gateway PC computes for every AIS ship the CPA (how close it will pass) and
  the TCPA (in how many minutes):
    WARNING  CPA under 0.5 nm within 10 min   (yellow on the maps)
    DANGER   CPA under 0.25 nm within 6 min   (red on the maps + the
             driver screen; alarm COLLISION RISK, video SAVE)
  (gateway PC settings gateway.json "avoid": warn_nm, warn_min,
  danger_nm, danger_min, safe_nm, clear_nm, min_kn ...)
  WHAT HAPPENS IN EACH MODE:
    AUTO       automatic, step by step, already at the WARNING level (early,
               while there is still room):
               1. slow down (half speed, at least 4 kn) and re-check after
                  20 s;
               2. still too close -> a route that passes ASTERN of the ship
                  (starboard turns first, then port; it never crosses ahead
                  of a ship's bow, keeps 0.5 nm, and passes the depth check
                  of part L). The route is drawn on both maps.
               3. clear (going back is safe) -> the boat rejoins its leg.
               Every decision is written to the gateway PC's audit log.
    HDG LOCK   at the WARNING level too: the same route as a PROPOSAL on the
               driver screen ("Steer
               074 and slow to 4 kn?") - ACCEPT changes the locked heading,
               REJECT keeps it (no new proposal for 60 s, the alarm stays).
               When clear: "Back to heading 344?" (ACCEPT / REJECT). The
               throttle stays with you. Only the driver screen (or the
               captain in SINGLE-OPERATOR mode) can answer.
    MANUAL / REMOTE MANUAL   alarm only: you steer.
    STANDBY / TRAINING       nothing.
  COLLISION RISK - DRIVER DECISION: the situation can't be solved safely by
  the gateway PC (two or more dangerous ships, a ship that is turning, old / stale
  AIS data, no safe route): in AUTO the boat slows to 4 kn and KEEPS ITS
  COURSE (never an unchecked route). YOU decide: take the joystick.
  The boat only applies what the gateway PC asks in AUTO (or after your ACCEPT in
  HDG LOCK), and only within all its own rules (power limit, joystick
  wins, STANDBY wins). If the gateway PC goes silent during an avoidance, the boat
  holds its heading, slows to 4 kn and sounds DRIVER DECISION.
  The boat also checks the gateway PC's request itself: an avoidance heading must
  come with a speed reduction, and one more than 150 deg off the leg
  (parameter nav_max_dev) is not steered (the boat slows, DRIVER DECISION);
  an accepted HDG LOCK heading counts only if it came while HDG LOCK was on.
  Collision and shallow-water alarms do NOT lower the power limit (slowing
  down is done by the speed request itself).
  Screen 2, tab "AIS": the ship list (name, distance, bearing, CPA,
  TCPA, age), click a ship for its details.

N. OBSTACLE DETECTION WITH THE FRONT CAMERA (eWaSR, AI)

  swimmers, rocks) become obstacles with a bearing and a ROUGH distance.
  IT NEVER STEERS THE BOAT AND NEVER GIVES MORE THROTTLE. It does not see
  everything (night, fog, glare, small things far away): keep a lookout.
  Licence: model and code Apache-2.0, test pictures MaSTr1325 CC BY 4.0 -
  both allowed for this project (gateway\vision\README.md).
  STAGES (screen 2, Tools - Cameras; every change is logged):
    1 overlay + log    (ON)  colours over the front camera on the driver

    2 alarm + SAVE     (ON)  an obstacle in the path ahead (only while
                             driving, not moored in STANDBY): alarm
                             OBSTACLE AHEAD + video SAVE. No effect on the

    3 slows AUTO       (OFF) AUTO slows to 3 kn (idle when nearer than

  DRIVER SCREEN: "VISION ACTIVE 2.0" in the bottom line; the overlay on / off

    ACTIVE     working
    PAUSED     the gateway PC's main jobs need the CPU, or its CPU is hot / throttling
    DEGRADED   too slow (below 1 picture / s) or the camera gives no pictures
    OFFLINE    switched off, model missing, crashed (it restarts by itself)
  If vision stops working while it slows AUTO down, the slowdown STAYS until
  the driver presses CLEAR SLOWDOWN (it is never released by itself).
  It runs on the gateway PC's CPU (no NVIDIA; measured load: gateway\README.md
  section 21). Setup and the model file:
  gateway\vision\README.md. Your own recordings can be tested on the PC:
     tools\bin\vision-python\python.exe gateway\vision\evaluate.py FILE.ts
  -> test_results\vision_eval\report.md (speed, detections, pictures).
  Samples for an own Saronic dataset (picture + mask) can be switched on
  (vision.samples on the gateway PC); they use at most 500 MB.

10. THE POWER LIMIT
-------------------------------------------------------------------------------
  * After EVERY power-up or reset: 30 % forward, 5 % reverse (of the full
    throttle travel). Never saved.
  * Raise, one step at a time (30 -> 50 -> 75 -> 100 %; reverse 5 -> 10 -> 15):
      1. "Raise fwd" (or "Raise rev") in the ground station,
      2. type the 4-digit code the window shows, "Send code",
      3. press CONFIRM on the joystick within 10 s (stick centred).
    Each step needs the whole sequence again. Wrong / old code: refused.
  * It drops back to 30 / 5 AT ONCE on: "Lower now", TAKE or a stick
    takeover, the STANDBY button, ANY alarm (incl. PC link lost, GPS lost,
    compass / joystick / gear fault), entering TRAINING, and after 2 min
    below 3 kn. The throttle then comes down at its normal rate (no sudden
    cut), but it can never go above the new limit.
  * In AUTO the leg speed is limited by it; the window shows "SPEED LIMITED
    BY POWER LIMIT".
  * Enforced in the lowest layer: app/servo.c, the only code that drives
    the throttle servo. The CPU1 monitor checks it again.

11. ALARMS
-------------------------------------------------------------------------------
  COMPASS LOST, GPS LOST, GPS SUSPECT (spoof flag, jump, speed, course,
  slow drag, second GPS, or a fix with impossible numbers - NaN, latitude
  beyond 90, ...), DEAD RECKONING LIMIT,
  ARRIVAL UNCERTAIN, ARRIVED, GEAR FAULT, TRAINING,
  JOYSTICK FAULT, JOYSTICK NOT CENTRED, JOYSTICK TOOK CONTROL,
  PC LINK LOST
  NOT NEUTRAL AT START   outputs not armed: gear not in neutral / stick held
  SAFETY MONITOR TRIPPED CPU1 forced idle + neutral (see chapter 12)
  EMERGENCY STOP         the e-stop switch is pressed: STANDBY, nothing else
                         until it is released (chapter 6A)
  CONTROL LOOP OVERRUN   a control cycle took longer than 50 ms
  LOG FAILURE            SD card missing / full / failing (control goes on)
  GATEWAY LOST           the gateway PC is silent for 3 s (no mode change)
  SHALLOW WATER          AUTO: shallow water ahead (charts); the boat slows to
                         4 kn (part L)
  COLLISION RISK         an AIS ship will pass closer than 0.25 nm within
                         6 min (part M); AUTO avoids it, HDG LOCK proposes
  OBSTACLE AHEAD         the front camera sees an obstacle in the path (part N,
                         STAGE 2 / 3); a warning - only STAGE 3 slows AUTO
  COLLISION RISK - DRIVER DECISION  the gateway PC can't solve it safely (or went
                         silent during an avoidance): slow, keep course - YOU
                         decide (part M)
  AIS RECEIVER SILENT    no AIS message for 5 min at sea: antenna / receiver
                         (warning only, part J)
  SLAMMING               an impact harder than slam_limit_g: throttle reduced
                         one step, video SAVE; the power limit stays (only
                         with slam_red_reset = 1 it drops to 30 %) (part H)
  GATEWAY STORAGE        the gateway PC's SSD is missing / failing, or STORAGE FULL
                         (no mode change; SAVE refused while full)
  REMOTE LINK LOST       the remote station holding HELM disappeared; HELM
                         goes back to nobody (no mode change)
  CHANNEL FALLBACK       the internet channel you chose (MANUAL) failed; the
                         gateway uses the next working one (no mode change)
  REMOTE DRIVING LINK LOST  remote joystick data too old / missing: idle,
                         neutral, gyro heading hold; STANDBY after 5 s
  LOW BATTERY            the 12 V bank (filtered over ~30 s) stayed below
                         batt_low_v (11.8 V, TO CONFIRM) for 60 s; clears
                         0.3 V higher. ADVISORY: no mode change, the power
                         limit STAYS (the way home may need the power), no
                         video SAVE. The acknowledge clears it once the bank
                         is back above 12.1 V. (In the log / telemetry it is
                         bit 1 of the SECOND alarm word, alarm_bits2: the
                         first word is full.) Not measured at all (divider not wired,
                         converter dead): the NOTICE "NO VOLTAGE DATA" after
                         5 s - no alarm, nothing else changes.
  RELAY BOARD SILENT     the relay board gave no valid reply for 3 s (RS485)
                         / its node 30 silent, not OPERATIONAL, ERROR or
                         the CAN bus down (DroneCAN board, step 11f)
                         while a relay table is loaded. ADVISORY: states
                         shown unknown, no new relay command; no mode
                         change, the power limit stays, no buzzer.
                         Clears by itself when the board answers (second
                         alarm word, bit 2). Never shown without a fitted
                         relay board.
  DP THRUSTER HOT        a DP thruster used its heat budget (boat file
                         run_s): it stays at 0 until it rested (rest_s).
                         An ordinary alarm (buzzer, power limit back to
                         30 / 5). In DP the DP ends (thrusters 0, STANDBY:
                         it can't hold with one thruster); no new DP until
                         it rested. The acknowledge keeps it while the
                         thruster is still hot (second alarm word, bit 3).
  DP OFF SPOT            DP SPOT / JOG: the boat is farther than spot_alarm_m
                         (boat file, 15 m) from the spot. ADVISORY: DP keeps
                         trying, the power limit stays; more than 50 m or 2
                         min off -> thrusters 0, STANDBY (second word, bit 4).
  DP OVERPOWER           both DP thrusters at their limit for 10 s: the wind
                         / current is too strong. ADVISORY (bit 5).
  CAN NODE LOST          (DroneCAN servo nodes, only when a CAN bus is fitted)
                         a REQUIRED node (throttle 20 / steering 21 / gear 22)
                         sent no heartbeat for 1.5 s, is not OPERATIONAL,
                         reports ERROR / CRITICAL, or REBOOTED (its uptime
                         went back), or the bus is dead. An ordinary alarm
                         (buzzer, power limit 30 / 5) + STANDBY (idle +
                         neutral first); no mode but STANDBY while a required
                         node is lost or not seen yet. A rebooted node stays
                         lost until it ran 2 s and you acknowledge in STANDBY.
                         The relay board node (30) is only shown, never this
                         alarm. A node reporting WARNING = a notice only.
                         (Second alarm word, bit 6.)
  CAN BUS FAULT          the CAN bus is off / error passive for more than
                         100 ms (cable, termination, every node unpowered,
                         transceiver), the CAN controller did not start, or
                         a frame FROM OUR OWN NODE ID 10 is on the bus: the
                         old Pixhawk is still connected - it is node 10 too
                         and must NEVER be on the bus with the AURIX
                         (WIRING.md 3E). Same reaction as CAN NODE LOST; it
                         clears 3 s after the last such frame. A node asking
                         for a dynamic node ID (no fixed ID set) = a notice
                         only - set its ID with the DroneCAN GUI Tool.
                         (Second word, bit 7.) The node table (health, mode,
                         uptime, reboots, counters) is on the Bench page of
                         the USB laptop. The servos over CAN (step 11e,
                         chapter 12) stay off on the board (HAL_CAN_FITTED /
                         HAL_CAN_SERVOS 0) until the kit's CAN pins are
                         confirmed.

  Every new alarm drops the power limit to 30 / 5 and starts a black-box
  file (except the navigation warnings SHALLOW WATER, COLLISION RISK, DRIVER
  DECISION, OBSTACLE AHEAD, AIS RECEIVER SILENT, LOW BATTERY, RELAY BOARD SILENT, DP OFF SPOT and DP OVERPOWER: they
  never change the power limit; RELAY BOARD SILENT doesn't sound the boat's buzzer and
  doesn't block a power raise either). Acknowledge: STANDBY button in STANDBY, or "ACK ALARM" in
  the ALARMS panel (top right of screen 2). Both screens list every active
  alarm in ONE place (screen 1: under the right mirror; screen 2: top
  right), one per line, most severe first; an alarm not yet acknowledged on
  THIS PC flashes, the others are steady.
  An acknowledge clears only the alarms whose cause is gone: a compass /
  GPS / joystick fault, a lost link, a tripped monitor, a gateway problem
  ... that is still there stays on (from any station, also from shore).

  ON THE PC every alarm has a LEVEL (sounds, lamps: chapters 5B / 5D):
    WARNING  COMPASS LOST, GEAR FAULT, JOYSTICK FAULT, SAFETY MONITOR
             TRIPPED, REMOTE DRIVING LINK LOST, COLLISION RISK (+ DRIVER
             DECISION), SHALLOW WATER, EMERGENCY STOP, CAN NODE LOST, CAN BUS
             FAULT, NO DATA FROM THE BOAT
    ADVISORY ARRIVED, TRAINING, JOYSTICK TOOK CONTROL, AIS RECEIVER SILENT,
             LOW BATTERY, RELAY BOARD SILENT
    CAUTION  all the others
  (groundstation\alerts.py). The GENERAL WARNING / CAUTION lamps of the
  driver screen only silence this PC - they are not the boat's ALARM ACK.

12. SAFETY RULES BUILT INTO THE SOFTWARE
-------------------------------------------------------------------------------
  * Gear changes only at idle: idle -> wait -> neutral -> wait -> gear.
  * Every fault / STANDBY: idle + neutral FIRST, then steering off (the
    DroneCAN position servo: HOLD). Idle is commanded AT ONCE; neutral once
    the throttle servo must be at idle (thr_trav_s); until idle +
    neutral the onboard stick (from MANUAL) or the gyro (from REMOTE, or a
    joystick fault) keeps steering.
    Compass lost while moving (AUTO / TRAINING): gyro steering until
    stopped (or outboard to centre if the gyro is gone too). In HDG LOCK:
    gyro hold, the throttle stays with you; STANDBY once you have stopped.
    In MANUAL: alarm only.
  * Throttle rate limits; reverse limited; the power limit (chapter 10).
  * The joystick always wins; the STANDBY button always wins.
  * NEUTRAL-START INTERLOCK: after power-up the outputs only arm when the
    throttle is idle, neutral is confirmed (neutral switch if fitted) and
    the stick is centred - and the joystick must be there: no joystick
    seen (not plugged in, USB bridge not sending yet) = not armed, alarm
    NOT NEUTRAL AT START. Until then: STANDBY only, safety relay open,
    alarm after 3 s.
  * WATCHDOGS on all three cores (100 ms on core 0). A stuck loop resets
    the chip: everything starts again in STANDBY at 30 %.
  * CPU1 SAFETY MONITOR: checks every 1 ms, on its own: throttle above the
    power limit, gear moving with the throttle open, core 0 silent for
    200 ms. Then it forces idle + neutral + steering off + alarm + safety
    relay open, and core 0 can't undo it until a reset. Reaction in the
    simulator: 10-20 ms (one check), 220 ms for a frozen core 0.
  * Heading hold pauses (outboard held still) when there is no propulsion,
    so the angle estimate can't drift while you are stopped.
  * Logging can never block control (chapter 13).

DRONECAN SERVOS (STEP 11e - THE CODE IS READY, THE BOARD STILL USES PWM)
  The boat's throttle, steering and gear servos can be DroneCAN nodes
  (throttle 20, steering 21 = a 360 deg position servo, gear 22). The code
  for it is complete and tested in the simulator ("autopilot_sim all --can"
  = worst-case servos, throttle 6 s / steering 12 s lock to lock;
  "all --can-fast" = 2 s / 3 s). On the board it stays OFF
  (hal/hal_pins.h HAL_CAN_FITTED 0 and HAL_CAN_SERVOS 0) until the owner
  has checked the kit's CAN pins and the servo nodes on the bench
  (FIRST_TEST.md 3j). What changes with the DroneCAN servos:
  * Throttle UP is gentle (15 %/s), DOWN is faster (50 %/s); STANDBY, the
    e-stop, a lost link, a lost node, every fault and a monitor trip
    command IDLE AT ONCE (no rate limit - only the servo's own speed).
  * "Idle" for every rule that waits for it (gear change, steering off,
    ENGINE KILL, STARTER, generator, DP, restart) = where the throttle servo
    MUST be by now: the software assumes the slowest servo (thr_trav_s,
    6 s from full to idle). The gear servo moves only after that. A longer
    thr_trav_s is taken at once (STANDBY); a SHORTER one needs a joystick
    CONFIRM (it is logged) and is never saved.
  * After every boot the first command is THROTTLE IDLE; the gear gets no
    command for the throttle travel time; the steering gets NO command
    until a mode steers (no automatic centring). After a power-on the
    steering position is unknown: the first moves run at the worst-case
    speed without play compensation.
  * Lost commands (reset, bus fault, a dead AURIX): every servo HOLDS where
    it is. The throttle comes down by the AURIX (idle first after a boot),
    by CPU1's safe frames, or the engine is stopped (kill cord / e-stop /
    UNCREWED dead-man).
  * Throttle node lost: the gear is HELD (never an automatic neutral);
    CREWED = alarm + STANDBY; UNCREWED = ENGINE KILL at once (owner
    decision OD-3, the one exception to "kill only after idle + neutral").
  * Monitor trip: CPU1 sends its own safe frames every 20 ms (throttle
    idle, steering held, gear held until the throttle travel time, then
    neutral while the throttle node works); core 0's frames are cancelled.
    The servo power is never cut. Core 0's 10 ms actuator task stopping for
    100 ms is a trip too (MON_TRIP_CAN_TX).
  * The e-stop stops the ENGINE in every profile (hard-wired kill circuit
    contact, WIRING.md); the software ENGINE KILL stays UNCREWED only.
  * UNCREWED dead-man: a timer relay in the kill circuit, held "run" by
    pulses from CPU1 (P10.5, ~1.5 s): no pulses = the engine stops by
    itself (trip, frozen AURIX, throttle node lost, kill latched). Part,
    time and arming switch: TO CONFIRM (WIRING.md 3A). A warm reset in
    UNCREWED may stop the engine (the pulses restart only after the profile
    detection) - TO CONFIRM.
  * STEERING TRAINING for the position servo (TRAINING, from STANDBY, slow
    ahead in calm water): centre, small steps, large steps, a reversal
    staircase, a check run - it measures the servo speed per direction,
    the play (backlash), the turn gain K and the boat's time constant.
    Accept = saved in data-flash slot 5 (format 2; an old DC-motor result
    is refused: "NV DATA RESET" + "TRAINING NEEDED"). Without TRAINING the
    steering uses the worst-case speed and no play compensation.
  * With TRAINING: every direction change adds the measured play, the
    command never moves faster than the servo, and in steady calm-water
    HDG LOCK / AUTO the model adapts slowly (RAM only, K / tau within 0.7 -
    1.3 x TRAINING, the play only smaller, the speed never faster). On any
    doubt (sensor fault, node lost, a bound reached, a large model error)
    it goes back to the TRAINING values at once: notice STEERING MODEL
    RESET. The Control page shows the stored / adapted values, the
    confidence, the last reset reason and the throttle model.

WHAT THE BOAT REMEMBERS (DATA FLASH)
  Kept after power-off, on the chip: the TRAINING result, the joystick
  calibration, the joystick source + button map, the last AUTO program and
  the boot counter (log file names). NOT kept, by design: the power limit
  (every power-up starts at 30 / 5 %) and the parameters changed from the
  Config tab.
  * A save is written to the flash only in STANDBY (the boat not stopping):
    a program uploaded while driving is kept in memory and written at the
    next STANDBY; the screens show "NV save pending" meanwhile. The
    control loop never waits for the flash.
  * Every record carries a version and a checksum. A record that is
    unusable (bad checksum, an older firmware format, a corrupted flash)
    is NOT used: the defaults take over and both screens show the notice
    NV DATA RESET (log event NV) - check the joystick calibration / map,
    the TRAINING result and the program before leaving the dock. A power
    loss during a write keeps the previous record.
  * NV FAULT (a notice, no alarm): the data flash does not work; nothing is
    saved any more (everything is lost at power-off), the boat drives on.

  Lever does nothing             MOVE THROTTLE TO PICK UP: bring it to the
                                 yellow mark or to neutral.
  Map refused                    two functions on one button, or not in
                                 STANDBY.

19. TESTING (THE ACCEPTANCE TEST)
-------------------------------------------------------------------------------
Besides the normal tests (chapter 4 and tools\check.sh before every commit)
there is a big acceptance test that checks the WHOLE system. Run it before
sea trials and after big changes:

    tests\acceptance\RUN_ACCEPTANCE.bat          quick: about 10-15 minutes
    tests\acceptance\RUN_ACCEPTANCE.bat full     everything: several hours

(or: C:\msys64\ucrt64\bin\python.exe tests\acceptance\run_acceptance.py quick)
Extra install for the coverage part only:
    pacman -S mingw-w64-ucrt-x86_64-python-coverage

WHAT IT DOES
  fresh build        clones the project from GitHub into an empty folder and
                     builds / tests it there, following only this manual -
                     finds files or steps that only exist on this PC
  fault storm        2000 (quick: 200) random "bad days" of 5-30 min each in
                     the simulator, much faster than real time: sensor
                     failures, broken frames on every link, random joystick
                     and buttons, random PC commands, resets, a frozen core 0
                     ... After EVERY control step 21 safety rules (I1..I21,
                     e.g. "STANDBY always wins") are checked. It first proves
                     that the checks work (it plants 3 violations and they must
                     be caught).
  time wrap          the boat's millisecond clock runs over 49.7 days
  soak               24 h of boat time (AURIX, with logging) + a real-time
                     run of the gateway with cameras, recording, vision, AIS,
                     sync: memory, files, sockets, timing over time (a leak
                     shows as a growing line)
  day at sea         one long mission through everything (two parts: the
                     AURIX with its faults in simulated time, and the whole
                     system in real time) - a timeline table
  gateway storms     random traffic / channels / storage / vision / stations
                     against the gateway's own rules (I14-I17, I20, I21)
  coverage           which code the tests run at all (full only)

HOW TO READ THE RESULT
  test_results\acceptance_summary.txt: one line per part, PASS / FAIL, and
  the name of its log file next to it. In a log:
    PASS / FAIL lines   one per rule or step; FAIL = look closer
    "seed N"            a random run can be repeated exactly:
                          test_results\storm.exe --replay N
                        prints every event of that run; "minimal N events"
                        = the shortest list of events that still fails
    worst reaction      e.g. "worst 2.88 s" for STANDBY = the slowest the boat
                        took (idle + neutral) in all the runs
  A FAIL is not always a bug in the boat: it can be the test itself. The last
  full result, every finding and what to fix first: TEST_REPORT.md (project
  folder). The large outputs (logs, coverage pages, soak data) stay in
  test_results\ - not in git; delete it any time.
  What the PC can't test (real board timing, the gateway PC's speed, the sensors,
  the sea): TEST_REPORT.md section 4.

20. ACADEMY - FOR TRAINEES AND INSTRUCTORS
-------------------------------------------------------------------------------
The academy teaches the station and the boat on the SIMULATOR of this PC and
on recorded trips. Every academy window shows the banner "TRAINING -
SIMULATION" at the top. The details of every part are in chapter 7A ("THE
ACADEMY LEVELS" ... "THE TEST AREA"); this chapter is the path through it.
Screenshots of every academy window: docs/screens/academy/ (README.md).
The rules that never change:
  * the academy never connects to a boat - only the simulator on this PC
    (127.0.0.1:5760) or files; the one exception is the PRACTICAL TEST,
    which only WATCHES the boat and asks one confirm-only question;
  * the academy only ADDS gates: STANDBY, the onboard joystick, the 30 / 5 %
    start power limit, the onboard CONFIRM and the captain's ACCEPT stay the
    boat's own and can never be bypassed;
  * a level goes up ONLY through the practical test (examiner + onboard
    CONFIRM) - never through an exam, a mission, a quiz or anything online;
  * the Daskalio chart photos and drone photos are pictures for training,
    NEVER a navigation chart (the safety checks use only charts/).

[ACADEMY] THE ACADEMY WINDOW
  Ground station menu Academy -> "Open the academy" (its own window and
  process), or "python academy/academy_app.py --lang el". The list = every
  account with its level, expiry, lessons, exams, hours, currency and weak
  areas. Select YOUR account before you open a lesson / quiz / scenario /
  exam / mission - without one it is practice and nothing is logged.

[GUIDED TOUR] FIRST: THE GUIDED TOUR
  "Guided tour": every item of screen 1, screen 2, the tools window, the
  modes, the alarms, the lamps, the joystick and the panel buttons, with the
  Greek voice. Do it once completely before the lessons.

[LESSONS] SIMULATOR LESSONS (DRIVER first, then CAPTAIN)
  "Simulator lessons" -> "Start the simulator" -> pick a lesson -> Start.
  The required lessons of a level must be passed before its exam (a tick in
  the list). Checked from the simulated boat itself; Retry when too late.

[QUIZZES] QUIZZES
  "Quizzes": choice, picture and alarm-sound questions; under 70 % = a weak
  area in the instructor view - repeat that pool.

[SCENARIOS] EMERGENCY SCENARIOS
  "Emergency scenarios": react as on the boat; the reaction time counts. Read
  the debrief and use "Replay". One scenario every year for the renewal.

[VIDEO LESSONS] VIDEO LESSONS FROM REAL TRIPS
  "Video lessons": real trips with the HUD redrawn, decision points and
  spot-the-hazard questions (70 % to pass). The instructor makes them with
  the "Lesson editor" (faces / number plates blurred by hand).

[EXAMS] THE EXAM OF THE LEVEL
  "Exams": 15 questions, 80 % to pass, 3 attempts then 24 h wait. Online only
  in a session an instructor marked supervised. Passing does NOT change the
  level: it opens the way to the practical test.

[PRACTICAL TEST] THE PRACTICAL TEST ON THE BOAT
  Ground station on board: menu Academy -> "Practical test on THIS boat",
  CREWED only, the examiner logs in with 2FA, the test area must be set (the
  placeholder in git is refused), the wind / hours / calm water / start power
  limit are checked first. Each task is seen in the telemetry and approved
  by the examiner; at the end the ONBOARD joystick CONFIRM within 10 s. Then
  the level goes up and the instructor sends the levels file to the gateway
  (it takes effect at the next login, never mid-trip).

[ONLINE] FROM HOME (THE ONLINE ACADEMY)
  Remote desktop / SSH over Tailscale to the academy PC only (never a boat).
  Lessons, quizzes, scenarios, video lessons and missions work as on the PC;
  exams only in a supervised session; nothing online raises a level.

[3D SIMULATOR] THE 3D SIMULATOR (FUTURE - THE INTERFACE IS READY)
  Academy window -> "3D simulator". There is NO 3D world yet: this window and
  docs/academy_sim_interface.md are the ready interface for a future Godot
  simulator. What it does now:
    * "Lesson simulator": built-in (2D, default) or 3D (Godot). The 3D choice
      is used only while the 3D simulator is running (it writes a fresh
      hello file); otherwise the window says "3D not available - built-in in
      use". In BOTH cases the boat is the simulator on this PC (the same
      safety code): the 3D world only SHOWS it (the academy writes the boat's
      state at 5 Hz into academy/data/sim3d/live.jsonl).
    * Missions (content/missions/*.json, by level): pick one, "Start in 3D"
      writes the mission for the 3D simulator (an attempt is counted; some
      missions have a limit), "Collect results" reads the 3D simulator's
      results (score, passed / not passed) into the logbook - the best score
      and the attempts show in the list. A wrong or forged result is refused
      and said. A mission result NEVER changes a level.
    * "Import drone photos": the owner's DJI photos of the area (with GPS)
      become the 3D view's picture / terrain (copies without metadata in
      academy/data/sim3d/terrain/<area>/). Photos without GPS are skipped.
      They are NOT a chart and no safety check ever reads them.
  The academy never starts the 3D program and never takes a command from it:
  start it yourself (when it exists) and keep the academy window open.

[INSTRUCTOR] FOR THE INSTRUCTOR
  Once: "Academy key" -> the gateway's secrets.json "academy_key"; your own
  password + "2FA app" (a CAPTAIN level of your own). Then, per trainee:
    1. "New account"; the trainee follows the path above (tour -> lessons ->
       quizzes -> scenarios -> video lessons -> exam).
    2. Watch the instructor view: weak areas (pools / lessons under 70 %),
       expiry (reminder 30 days before), currency (90 days).
    3. Supervise online exams ("Supervise online session", your 2FA login).
    4. Set the test area on site (menu Academy -> "Practical test area";
       W30: the real Daskalio bay + ramp are still to be set) and examine
       the practical test on the boat.
    5. "Make the gateway file" -> the ground station sends it (menu Academy
       -> "Send the academy levels to the gateway").
    6. Every year: "Renew" (DRIVER refresher; CAPTAIN + a check ride every 24
       months); "Certificate PDF"; "Backup" to a second shore PC / USB disk.
    7. 3D missions: edit / add content/missions/*.json (commented; the test
       academy/test_academy.py checks every file) and the 3D simulator's
       drone photos ("Import drone photos").
  Lowering a level is always possible ("Set level"); raising it never is,
  except through the practical test.
