1. WHAT THIS PROJECT IS
-------------------------------------------------------------------------------
An autopilot for a boat, running on the Infineon KIT_A2G_TC375_LITE board
(AURIX TC375, three CPU cores). There are two variants:

  * SMALL BOAT (default): outboard engine. The software controls the steering
    motor (no angle sensor: the angle is estimated), the throttle servo and
    the gear servo (Forward / Neutral / Reverse). It uses compass, gyro and
    GPS. Driving modes: MANUAL (joystick), HEADING LOCK and AUTO (waypoint
    program). It navigates without GPS (dead reckoning), calibrates itself
    (TRAINING), limits the engine power until you raise it on purpose, and
    logs everything to an SD card.
  * BIG BOAT: rudder with an angle sensor, heading hold only.

The board has not arrived yet. All of the logic is written and tested in a
PC simulation with a simulated boat. The parts that talk to the real
hardware are mostly empty "stubs" for now (see chapter 17).

The three cores:
  core 0  the control loop (20 Hz): modes, steering, engine, PC link
  CPU1    an independent safety monitor (checks core 0 every 1 ms)
  core 2  the logger (writes the SD card)

A PC ground station shows the boat live and sends commands, over the
board's USB cable or to the simulator.

Two kinds of joystick can drive the boat (chosen in the ground station):
the hard-wired analog joystick, or a USB Thrustmaster T.16000M stick +
TWCS throttle, read by a small Teensy 4.1 "bridge" board (chapter 8).

2. WHAT IS IN WHICH FOLDER
-------------------------------------------------------------------------------
  app/            The autopilot itself. Pure C, no hardware code. The same
                  files run on the board and in the PC simulation.
     smallboat.c    small-boat controller: modes, engine, steering, faults
     modes.c        mode manager: the ONLY place that changes the mode
     autopilot.c    steering core (heading hold, outboard angle estimate)
     program.c      AUTO waypoint programs (check, store with checksum)
     powerlim.c     power limit (30 % / 5 % at start, raise / drop)
     servo.c        the ONLY code that writes the throttle servo
     monitor.c      the independent safety monitor (runs on CPU1)
     joystick.c     the joystick, whatever its source (analog or USB)
     joybridge.c    USB joystick: frames from the bridge, fault checks
     joymap.c       joystick source + USB button map (saved with checksum)
     jsframe.c      the bridge frame format (also compiled into the bridge)
     gear.c, throttle.c, nav.c, dr.c, training.c, calib.c
     proto.c, link.c       PC link (frames, telemetry, commands)
     timing.c              CPU time per cycle, overruns
     logq.c, logrec.c, logcore0.c, logfields.h, logger.c   logging
  hal/hal.h       The list of hardware functions the app may use.
  hal/hal_tc375.c The real board versions of those functions (mostly stubs).
  Cpu0_Main.c     core 0: start-up, watchdog, the 20 Hz loop.
                  "#define BOAT_VARIANT_BIG" at the top selects the big boat.
  Cpu1_Main.c     CPU1: the safety monitor loop (1 kHz).
  Cpu2_Main.c     core 2: the logger loop.
  sim/            PC simulation, all tests, simulated boat for the ground
                  station. NOT part of the board build.
  groundstation/  PC ground station and log tools (Python).
  gateway/        Raspberry Pi 5 gateway software (Python): remote access,
                  log copy, cameras, sync. Setup step by step:
                  gateway/README.md.
  bridge/         Teensy 4.1 firmware for the USB joystick (PlatformIO).
                  Setup step by step: bridge/README.md.
  tools/          mapreport.py: memory report from the ADS build.
  WIRING.md       Wiring: joysticks (analog and USB bridge), panel buttons,
                  servos, SD card, USB.
  CLAUDE.md       The project rules (also read by Claude).
  MANUAL.txt      This file.
  Libraries/, Configurations/
                  Generated by AURIX Development Studio. NEVER edit them.

3. WHAT TO INSTALL
-------------------------------------------------------------------------------
Already installed on this PC: everything in this list.
On a new PC, install:

  a) MSYS2 (https://www.msys2.org), which provides gcc and Python. After
     installing, open "MSYS2 UCRT64" from the Start menu and run:

       pacman -S mingw-w64-ucrt-x86_64-gcc
       pacman -S mingw-w64-ucrt-x86_64-python mingw-w64-ucrt-x86_64-tk
       pacman -S mingw-w64-ucrt-x86_64-python-pyserial
       pacman -S mingw-w64-ucrt-x86_64-ffmpeg     (video, recording, tests)

     Then add  C:\msys64\ucrt64\bin  to the Windows PATH (Start -> "Edit
     environment variables" -> Path -> New).
     (Or python.org Python: tick "Add python.exe to PATH", then
      pip install pyserial )

  b) AURIX Development Studio (ADS) from Infineon, for building and flashing
     the board (includes the TASKING compiler and the USB debugger driver).

  c) Git (https://git-scm.com) and VS Code. The project is on GitHub:
       https://github.com/alextrygons/trygons-c2.git

  d) Only for the USB joystick bridge: in VS Code, Extensions -> install
     "PlatformIO IDE". It downloads the Teensy compiler by itself the first
     time you build bridge/ (details: bridge/README.md).

  e) MediaMTX (video relay, for the camera tests and the demo), into
     tools\bin\ of the project (not in git):
       C:\msys64\ucrt64\bin\python.exe tools\get_mediamtx.py
     (The demo asks to do it when it's missing. Check: python
      gateway\toolpaths.py shows where ffmpeg and MediaMTX are.)

  Check in a terminal (VS Code: Terminal -> New Terminal):
       gcc --version
       C:\msys64\ucrt64\bin\python.exe --version

6. THE BOARD (AURIX TC375 LITE KIT)
-------------------------------------------------------------------------------
  1. Open AURIX Development Studio, open the workspace with TRYGONS_C2.
  2. Build: the hammer icon (sim/, groundstation/ and tools/ are excluded).
  3. Flash and run: board on USB, Debug (bug icon), then Resume (F8).
  4. Memory report after a build:
       C:\msys64\ucrt64\bin\python.exe tools\mapreport.py "TriCore Debug (TASKING)\TRYGONS_C2.map"
     (the free TASKING licence only runs inside ADS: build there first.)

  Expected memory (before the first ADS build; from the compiled objects
  + each core's stacks / CSA; iLLD + start-up code add a few KB on core 0):
       sh tools/check.sh      (or: python tools\mapreport.py --objects <folder with .o>)
     core 0 RAM        119 KB of 240 KB (50 %)
     CPU1 RAM           12 KB of 240 KB ( 5 %: only the safety monitor + stacks)
     core 2 RAM         78 KB of  96 KB (81 %: logger + 1/4 of the black box)
     LMU blocks 0/1/2   54 KB of  64 KB each (84 %: 3/4 of the black box)
  The 60 s black box (1200 records x 184 B = 216 KB) is split in 4 chunks:
  core 2's RAM + the three LMU blocks. CPU1's RAM must stay below 60 %:
  mapreport.py says FAIL (and the gate fails) above that.

  Watchdogs are ON. When you stop the program in the debugger the
  watchdogs are paused too (normal for AURIX). If the board keeps
  resetting, the loop is too slow or stuck: look at the System tab and the
  log (EV_BOOT shows the reset reason).

7. HOW THE BOAT BEHAVES: MODES, BUTTONS, JOYSTICK
-------------------------------------------------------------------------------
MODES
  STANDBY    engine idle, neutral, steering off. Power-up and after faults.
  MANUAL     the joystick: stick left/right = outboard angle (full range),
             forward/back = throttle ahead/astern (centre = idle + neutral).
             Gear changes always go idle -> neutral -> gear, however fast
             you move the stick.
  HDG LOCK   press HDG LOCK on the panel: the autopilot holds the heading
             the boat has now. -1/+1/-10/+10 (panel or PC) change it. The
             throttle stays on the stick (ahead and astern) - you stay in
             HDG LOCK. In reverse the outboard is held straight. Moving the
             stick sideways takes over (MANUAL).
  AUTO       a waypoint program (up to 50 waypoints). Each waypoint has a
             leg speed, an arrival radius and an action: continue / slow
             down / stop in neutral. At the end: stop + alarm (or hold the
             heading slowly). AUTO starts only with the PC "AUTO START"
             AND the joystick CONFIRM within 10 s (stick centred). Pause,
             resume (+ CONFIRM) and skip from the PC. Line following,
             speed control, rough-water slow-down, dead reckoning without
             GPS, GPS integrity check: all as before.
  TRAINING   outboard calibration, started from STANDBY by the PC.

  Mode changes allowed (all others are refused and logged):
     from \ to   STANDBY MANUAL HDG_LOCK AUTO TRAINING REMOTE
     STANDBY        -      yes     yes    yes    yes     yes
     MANUAL        yes      -      yes    yes    no      no
     HDG_LOCK      yes     yes      -     yes    no      yes
     AUTO          yes     yes     yes     -     no      yes
     TRAINING      yes     yes     no     no      -      no
     REMOTE        yes     yes     no     no     no       -
  (REMOTE = REMOTE MANUAL, the shore joystick, chapter 9 part D)
  Extra rules: only the joystick enters MANUAL; MANUAL is left only with
  the stick centred; AUTO needs compass, GPS, a valid program and CONFIRM;
  TRAINING only from STANDBY by the PC; nothing but STANDBY until the
  outputs are armed (chapter 12).

THE JOYSTICK ALWAYS WINS (analog or USB - the rules are the same; the
USB lever has a few extra ones, chapter 8)
  * Take over from ANY mode: stick sideways past 15 % for 0.1 s, forward /
    back (not in HDG LOCK, where that is the throttle), or TAKE. Chirp.
    An AUTO program is suspended (resume later: PC + CONFIRM).
  * Give back: CENTRE the stick, then joystick AUTO (back to HDG LOCK if
    that was interrupted, otherwise STANDBY) or panel HDG LOCK. Not
    centred: refused + chirp. The PC can't take control from the stick.
  * CONFIRM only answers a request from the PC (AUTO start / resume, power
    raise). It counts only with the stick centred and the joystick armed.
    Nothing pending: nothing happens. It never changes the mode by itself.
  * At power-up the stick must be centred, otherwise it is ignored and the
    outputs stay off (alarm) until you let go.
  * Broken wire while it drives: idle, neutral, STANDBY; the gyro holds
    the course until idle + neutral, then the steering stops.

THE STANDBY BUTTON ALWAYS WINS
  Every mode -> STANDBY (idle + neutral first, then steering off). The
  throttle closes fast in STANDBY: idle within about 1 s from full
  (parameter stop_rate_pc_s, 100 %/s; normal driving and a planned arrival
  stop keep 40 %/s). Until idle + neutral is reached the boat is still
  steered:
    * from MANUAL: your stick keeps steering the outboard (even if you
      still hold it), then the steering stops;
    * from REMOTE MANUAL: the shore stick is ignored at once, the gyro
      holds the course;
    * from HDG LOCK / AUTO: the heading is held (gyro if the compass is
      gone).
  A stick that is still held can't take control back until it was centred.
  While the stick is held, nothing else can be engaged either: the HDG
  LOCK button is refused (short chirp), AUTO start / resume, remote
  driving and TRAINING are refused with "centre the joystick". Let go of
  the stick (centre), then engage.
  The PC can't override the button. In STANDBY the button acknowledges
  alarms.

AUTO PROGRAM - HOW TO
  1. Program tab: add waypoints (or tick "click adds" and click the map),
     set leg speed, radius, action; choose the end action.
  2. "Upload to boat". The boat checks it (coordinates, number <= 50, leg
     length 10 m .. 50 km, speeds within the maximum, radius 5..500 m) and
     stores it with a checksum (kept after power-off).
  3. Raise the power limit if you want more than ~7 kn (chapter 10).
  4. AUTO START, then CONFIRM on the joystick within 10 s.


-------------------------------------------------------------------------------
8. THE USB JOYSTICK (THRUSTMASTER T.16000M + TWCS)
-------------------------------------------------------------------------------
WHAT IT IS
  The T.16000M stick steers (left / right = outboard angle). The TWCS
  throttle has a lever that STAYS where you leave it (it has no spring),
  with a NEUTRAL ZONE in the middle (45-55 % of its travel):
      above the neutral zone  = forward      (further = more throttle)
      inside the neutral zone = idle + neutral
      below the neutral zone  = reverse
  Gear changes always go idle -> neutral -> gear, however fast you move it.
  Both plug into a small powered USB hub, the hub into the Teensy bridge,
  the bridge into the AURIX (WIRING.md section 6). If anything in that chain
  fails - a plug, the hub, the Teensy, the wire - the boat sees JOYSTICK
  FAULT within 0.15-0.2 s, exactly like a broken wire on the analog stick:
  if the joystick was driving: throttle idle + neutral, STANDBY, alarm;
  the gyro holds the course until idle + neutral, then the steering stops.

  The T.16000M and the TWCS are NOT waterproof: dry console only.

SWITCH THE BOAT TO THE USB JOYSTICK (once)
  1. Ground station, Joystick tab: Source = "USB bridge", Throttle = "lever".
  2. "Factory default (T.16000M + TWCS)" fills in the default buttons.
  3. Boat in STANDBY -> SAVE TO BOAT. It is stored with a checksum and used
     at every power-up. (Back to the wired joystick the same way.)

DEFAULT BUTTONS (change them with "Map buttons", below)
     TAKE       stick trigger                  (stick button 1)
     STANDBY    stick thumb button             (stick button 2)
     AUTO       TWCS button 1
     CONFIRM    TWCS button 4  (clearly apart from AUTO)
     HDG LOCK   TWCS button 3
     -1 / +1    TWCS hat left / right
     -10 / +10  TWCS hat down / up
     SAVE       stick button 3  (video SAVE on the gateway; optional)
  Which physical button is "TWCS button 1/3/4" depends on the TWCS: check
  with learn mode or the "now" column of the Joystick tab and map them where
  your thumb finds them. The panel STANDBY button stays and always wins.

POWER-UP
  The lever must be IN THE NEUTRAL ZONE and the stick centred. Otherwise:
  alarm "JOYSTICK NOT CENTRED" (= not in neutral), the joystick is ignored
  and the outputs stay off. Put the lever in neutral, let go of the stick.

TAKING OVER (any mode)
  * stick sideways (past 15 % for 0.1 s), or
  * the TAKE button, or
  * moving the lever more than 10 % away from where it was at the last
    hand-back (it was in neutral then, so: leaving the neutral zone).
    In HDG LOCK the lever IS the throttle, so there it does not take over.

THROTTLE PICKUP (no surprise jump)
  When the lever gets the throttle (MANUAL or HDG LOCK entered from STANDBY,
  AUTO or TRAINING), it first does NOTHING. The yellow banner says
  "MOVE THROTTLE TO PICK UP: lever to xx %" and the lever bar shows a yellow
  mark. Move the lever to that mark (within 3 %), or through it, or into the
  neutral zone: from then on the lever drives, starting from the throttle
  the engine has now.
    * Coming from AUTO: the engine keeps its throttle (lowered to the
      30 % power limit that every takeover sets) until you pick it up.
    * Coming from STANDBY: the engine stays at idle + neutral; the pickup
      point is the neutral zone.
  Example: the lever was left at 80 % and you take over: nothing happens
  until you bring the lever to the mark (or neutral).

LEVER AND POWER LIMIT
  Full lever forward = the CURRENT power limit (30 % at start), full lever
  back = the reverse limit (5 % at start). Raising the limit never makes the
  boat speed up by itself: if the lever is fully forward when you raise from
  30 to 50 %, the throttle stays at 30 %. Pull the lever back a little and
  push it forward again - now full lever is 50 %.

HAND-BACK
  Stick centred AND lever in the neutral zone, then AUTO (or panel HDG
  LOCK). Otherwise refused + chirp. (This means the engine is at idle when
  you hand back.)

CONFIRM (power raise, AUTO start / resume) on the USB button follows the
  same rules as before: only with the stick centred and the joystick armed,
  only for a pending PC request. The lever position does not matter here.

MAP BUTTONS (ground station, Joystick tab, boat in STANDBY)
  1. "Map buttons (guided)". Let go of everything, click Next.
  2. Move the stick fully right, hold, Next (steering axis found).
  3. Push the lever fully forward, hold, Next (throttle axis + direction).
  4. For each function press the button you want. A button already used
     for another function is refused at once ("already TAKE - press a
     different button"). TAKE, AUTO and CONFIRM must be mapped; the others
     can be skipped.
  5. SAVE TO BOAT. The boat checks again: TAKE, AUTO and CONFIRM on the same
     button -> refused ("two functions share a button").
  Note: the buttons keep their OLD job while you map them - pressing the
  TAKE button switches to MANUAL. That is on purpose (the joystick is never
  switched off). Press the panel STANDBY before saving.
  One function only: the "Map" button in its row.

LEARN MODE (on the Teensy, to see what is what)
  Teensy on the PC USB, VS Code -> PlatformIO -> Monitor, type  l  + Enter.
  Every button / hat / axis you move is printed with its code number.
  While learn mode is on the boat keeps the USB joystick disarmed.
  Other joysticks than the Thrustmaster: calibrate first ( c ), see
  bridge/README.md.

STATUS TO WATCH (Joystick strip / tab)
  "USB bridge: 100 frames/s, CRC errors 0, stick OK, throttle OK" is normal.
  Fewer frames/s, growing CRC errors: bad wire / interference. More than 5
  CRC errors per second, a frozen counter, an unplugged device, an invalid
  axis or no frame for 0.15 s = JOYSTICK FAULT (the reason is shown).
  For the first 5 s after power-up the bridge may still be starting (USB):
  no alarm then, the joystick is just not armed yet.

MEASURED IN THE SIMULATION (bridge + hub modelled)
  TAKE pressed -> mode change on the AURIX: average 34 ms, worst 60 ms
  (200 presses; target < 100 ms). Worst case by design: USB + hub 2 ms +
  frame period 10 ms + UART 3 ms + control loop 50 ms = 65 ms.

9. THE GATEWAY (RASPBERRY PI) AND REMOTE ACCESS
-------------------------------------------------------------------------------
THE IDEA
  A Raspberry Pi 5 on the boat is the only way in from the internet. The
  AURIX is NEVER on the network: it talks only to the Pi, over a cable
  (UART, the same frames with checksum as the USB laptop link). The Pi sits
  on the boat LAN behind the Teltonika router; shore PCs and the iPhone
  reach it only through a VPN (Tailscale) that the boat opens itself -
  no open ports, works behind the 4G operator's CGNAT.
  The USB laptop, the onboard joystick and the STANDBY button work exactly
  as before, with or without the Pi.
  Setup step by step: gateway\README.md.

A. THE GATEWAY LINK (AURIX <-> Pi)
  * UART 921600 baud (AURIX ASCLIN1: P15.0 -> Pi GPIO15, P15.1 <- Pi GPIO14),
    WIRING.md section 7.
  * The AURIX sends the Pi: telemetry, and a COMPLETE COPY of its log (every
    record it writes to its SD card, numbered). The Pi writes it to its USB
    SSD as .TLG files (aurix_logs\YYYYMMDD\P<boot>_<file>.TLG) - readable with
    logview.py / log2csv.py like the SD card files.
  * If the cable is too slow at some moment, the AURIX drops records for the
    Pi FIRST - never control traffic. The Pi notes the missing numbers in
    gaps.csv. The AURIX SD card is always complete: it stays the independent
    black box.
  * The Pi sends a status once a second (its "I'm alive"). Silent for 3 s:
    alarm GATEWAY LOST. Nothing else changes (no mode change) - unless you
    are driving remotely (part D).
  * The Pi's SSD missing / failing: alarm GATEWAY STORAGE; everything else
    keeps running. The Pi's own SD card holds only the operating system.
  * TIME: the AURIX sends GPS time to the Pi once a second; the Pi sets its
    clock from it, so the boat log, the gateway logs and the video all have
    the same time.
  * Ground station, System tab: "gateway (Pi): OK / LOST, Pi log copy up to
    record N, gaps".

B. USERS, ROLES AND HELM
  * Every station logs in to the gateway (user + password, or a key).
    VIEWER = watch only. HELM = may hold HELM.
  * Only ONE station holds HELM; only its commands are carried out (the
    AURIX checks it; others get "NOT HELM"). The top bar of the ground
    station shows "HELM: YOU - ..." or who has it; buttons "Take HELM" /
    "Release".
  * A station ON THE BOAT (USB laptop, boat LAN) can always take HELM, also
    from a remote one. A remote station only when nobody has it. The USB
    laptop takes a free HELM by itself.
  * The onboard joystick and the STANDBY button still beat everything.
    Power raise, AUTO start / resume and remote driving still need the
    joystick CONFIRM on the boat - remote can never do them alone.
  * Every command carries station, number and time; the gateway refuses
    duplicates, old ones (more than 2 s), out-of-order and too many. A PC
    with a wrong clock is fine (the gateway measures the difference).
  * Slow or far links get reduced telemetry (2 times a second, the
    essentials) automatically; the System tab shows every station's
    latency.
  * Remote HELM station lost: alarm REMOTE LINK LOST, HELM back to nobody,
    no mode change (remote driving: part D).
  * iPhone: http://trygons-gw:8080 over the VPN, view only (HELM from the
    web page only if switched on in the gateway config).
  * Audit log on the Pi: who connected, who held HELM, every command and
    its answer. Security rules: gateway\README.md section 12 - please do
    all of them (change ALL default passwords, VPN only, cameras without
    internet, separate networks).
  * Connect the ground station through the gateway:
      python app.py gw:trygons-gw:5761     (asks for user + password)

C. INTERNET CHANNELS (router Teltonika RUT901)
  Channels: 4G (SIM 1), 4G SIM 2, RF (future), STARLINK.
  STARLINK = EMERGENCY ONLY: metered, never used for sync, and in AUTO
  only when every other channel is down.
  The RUT901 has two SIM slots but one modem: only one SIM works at a time
  (switching takes 30-90 s; SIM 2 shows "standby").

  Ground station, Network tab: every channel with up/down, internet,
  latency, loss, signal (4G), data used today / this month; the active one
  marked ">". Buttons:
    AUTO           failover by priority (4G, 4G SIM 2, RF); STARLINK only when
                   all are down; back to a normal channel when it has been
                   stable for 60 s.
    MANUAL <ch>    use this channel; if it has no internet for 30 s ->
                   the next working one + alarm CHANNEL FALLBACK; back when
                   it is stable again. STARLINK asks "EMERGENCY LINK -
                   metered data" first. The fallback is STARLINK only if no
                   normal channel works (your chosen one included).
    MANUAL STRICT  only this channel, never switch. Only from a station on
                   the boat, with a warning.
    KEEP           every switch you ask for is a TRIAL: press KEEP within
                   60 s (over the new link). If you can't (the new link is
                   dead), the gateway goes back to what worked - you can
                   never lock yourself out from shore. It goes back to
                   STARLINK only if you had chosen STARLINK yourself;
                   otherwise it picks again (a normal channel first).
  Only the HELM station or a station on the boat may change the channel.

  While STARLINK is active: big "STARLINK - EMERGENCY LINK" banner, data
  saver ON (reduced telemetry, cameras front only, low - part E), sync
  stopped (part G), data counter for this session and the month, warning
  at the monthly limit you set (gateway.json, monthly_warn_gb, 20 GB).

  Setup of the RUT901 and Starlink: gateway\README.md section 13 (LAN
  range 10.42.0.x FIRST, then Starlink in bypass mode on the WAN port,
  failover with health checks, SSH key for the Pi).

D. REMOTE JOYSTICK DRIVING FROM A SHORE PC (mode REMOTE MANUAL)
  RULE: somebody is ALWAYS on board while the boat is driven remotely.
  Priority, always: STANDBY button > onboard joystick > remote joystick >
  autopilot modes.

  On the shore PC: plug in a USB joystick (e.g. T.16000M + TWCS; any
  standard joystick works). Ground station connected through the gateway
  (gw:...), Remote tab:
    1. "Find joysticks" shows the devices with their numbers. Choose the
       device + axis for steering and for the throttle, "invert" if it goes
       the wrong way, "lever" for the TWCS. Save.
    2. Take HELM. Tick "send my joystick (30 Hz)".
    3. REQUEST REMOTE DRIVING. The boat shows "PRESS JOYSTICK CONFIRM -
       REMOTE DRIVING": the person ON BOARD presses CONFIRM within 10 s.
       The mode becomes REMOTE MANUAL (blue).
    4. Drive: stick X = outboard angle (rate-limited, 20 deg/s), lever =
       throttle with the neutral zone and THROTTLE PICKUP like on board
       (chapter 8). Maximum 20 % forward / 5 % reverse (and never above the
       power limit). Slamming reduction applies (part H).
    5. RELEASE when done (-> STANDBY: idle, neutral, steering off).
  STANDBY button while driving remotely: the shore stick is ignored at
  once; the gyro holds the course until idle + neutral, then steering off.
  It also ends when: the onboard joystick moves or TAKE is pressed
  (-> MANUAL at once), STANDBY is pressed, any fault, a station on board
  takes HELM, the remote driver's link fails.

  LINK PROBLEMS: joystick data older than 0.3 s, a gap of 0.3 s, or a link
  latency over 0.4 s -> at once: throttle to idle, neutral, the outboard
  holds the heading on the gyro, alarm REMOTE DRIVING LINK LOST. After 5 s
  without the link: STANDBY. It NEVER starts again by itself - the request
  + CONFIRM on board is needed again.
  The joystick packets travel by UDP (signed with a key the gateway gives
  at login): a lost packet is simply replaced by the next one 33 ms later.
  (By TCP, one lost packet would hold everything for 0.2-0.6 s and the boat
  would declare LINK LOST every few seconds on 4G.)
  Measured in the simulation (4G, ~80 ms round trip, 1 % packet loss):
  stick move on shore -> visible in the boat's telemetry: median ~185 ms,
  max ~230 ms; 60 s of driving without a single LINK LOST.

E. CAMERAS (4 x TP-Link Tapo C310)
  FRONT-1 (main), FRONT-2 (backup), REAR-LEFT, REAR-RIGHT. Cable (Ethernet),
  on their own camera network behind the Pi; they have NO internet (the
  cloud is not used). The Pi relays the video (MediaMTX, no re-encoding).
  Video is never needed for safety: a camera problem never changes the mode.

  Ground station, Cameras tab (the big driver screen comes in part I):
    Full          front HIGH, mirrors LOW
    Front only    front LOW, mirrors off
    Mirrors only  rear cameras LOW
    All off       no video (no data used)
  Only what you asked for is sent over the internet. On STARLINK (or with
  data saver) only the front camera LOW is allowed - "override" works with
  data saver on 4G, never on STARLINK. Per camera: state (OK / FROZEN /
  DOWN), bitrate in and out, total.
  FRONT-1 frozen or gone (no new picture for 1 s) -> the front view switches
  to FRONT-2 by itself ("FRONT-1 LOST - showing FRONT-2"), and back when
  FRONT-1 has worked again for 2 s. A frozen picture always shows
  VIDEO FROZEN within 1 s. Remote driving warns if no front camera is live.
  Measured in the simulation: about 135 ms on the boat LAN, ~190 ms over 4G
  (plus the camera's own delay, about 0.3-1 s for a Tapo - not measured).
  Camera setup, firmware updates (the "Camera internet 30 min" button,
  only from a station on board), wiring: gateway\README.md section 14,
  WIRING.md section 8.

F. VIDEO RECORDING: RING BUFFER AND SAVE
  The Pi records all 4 cameras (full quality) all the time, in 1-minute
  files on its SSD. Only the last 5 / 10 / 20 / 30 / 60 minutes are kept
  (the "ring buffer"; Cameras tab -> ring buffer, HELM or a station on board).
  Recording never uses the internet and never affects driving.

  SAVE keeps the whole ring window before it + 2 minutes after it (all
  cameras), with: time, position, speed, heading, mode, alarms, what
  triggered it, and the name of the AURIX log file (record number) of that
  moment. A SAVE starts by:
    * the SAVE button (Cameras tab; the big driver screen in part I),
    * the SAVE button on the boat's USB joystick (default: stick button 3;
      "Map buttons" in the Joystick tab) or on the shore PC's joystick
      (shore_joystick.json "save_button", default button 3),
    * automatically: a new alarm (not "arrived"), a fault, the joystick
      taking over from HDG LOCK / AUTO / REMOTE / TRAINING, STANDBY because
      of a fault, slamming over the red limit (part H).
  Several triggers close together are one SAVE (it gets longer). VIEWERs
  can't SAVE.
  Where: <SSD>\video\events\YYYYMMDD-HHMMSS_<trigger>\<CAMERA>\*.ts and
  event.json. The files play in VLC.
  Watch it next to the log: python logview.py -> "Open event..." (choose
  event.json: video + its log, cursor at the trigger) or "Video folder...";
  choose the camera, click in the plots or press Play. Accuracy about 1 s.

  SSD space (1 hour of video from 4 Tapo C310 at full quality is about
  3-4 GB, 4 x ~2 Mbit/s - check "GB/h" in the Cameras tab with the real
  cameras): when the SSD runs low the Pi deletes, in this order:
    1. the oldest ring buffer files,
    2. the oldest SAVEs that are already copied to the shore PC (part G),
  but NEVER a SAVE that is not on the shore PC yet. If that is not enough:
  STORAGE FULL (alarm GATEWAY STORAGE on the boat): new SAVEs are refused,
  the ring buffer keeps running. Free space: sync to the shore PC, or copy
  the events away and delete them.
  A camera that stops recording (cable, power) is restarted every few
  seconds; the others keep recording. "not recording: ..." shows it.

G. SYNC TO THE SHORE PC
  The Pi copies its SSD to the shore PC by itself, over the VPN, whenever
  the boat is on 4G / 4G SIM 2 / RF (NEVER on STARLINK). In this order:
    1. black box / alarms   AURIX logs with an alarm, fault or SAVE in them,
                            and every SAVE's description (event.json)
    2. event logs           the audit log (who did what), log gaps
    3. telemetry logs       all other AURIX logs
    4. saved events         the SAVE video
    5. ring video           only if switched on (recording.ring_sync) - OFF
  * It only uses spare bandwidth: it measures its own ping to the shore and
    slows down at once when the link starts to queue (video, telemetry and
    commands stay fast). During REMOTE MANUAL it stops completely.
  * A broken connection continues where it stopped (checked with SHA-256).
  * A file counts as "synced" only after the shore PC has checked it. Sync
    never deletes anything; only when the SSD runs low does the Pi delete
    SYNCED data (part F).
  Network tab: SYNC state, speed, ping, what is waiting per class, the last
  confirmed file; on the shore PC also what it has received.
  The files arrive on the shore PC in <folder>\trygons-c2\ (same layout:
  aurix_logs, audit, video\events) - open them with logview.py.
  Setup: gateway\README.md section 16.

H. SLAMMING (hull impacts) AND AUTOMATIC THROTTLE REDUCTION
  A BNO085 motion sensor measures the vertical acceleration about 200 times
  a second. Shown and logged: the hardest impact (g), impacts per minute,
  and the "level" (running average of the impacts; it falls again when the
  water gets smooth).
    CALM     nothing happens
    YELLOW   level above 70 % of the limit: warning beep; the forward
             throttle is reduced one step (10 %) at once and again every 5 s
             while it stays yellow (never below 30 %)
    RED      one impact harder than the limit (default 3.0 g): red alarm
             SLAMMING, one more step down at once, and a video SAVE.
             The power limit STAYS (setting slam_red_reset = 0, "STEP",
             the default): a sudden drop to 30 % can be dangerous in a
             following sea (a wave from behind). slam_red_reset = 1
             ("LIMIT_RESET") brings back the old behaviour: the power
             limit also drops to 30 %, like for every other alarm.
  It only ever REDUCES the throttle, in every mode (MANUAL, HDG LOCK, AUTO,
  REMOTE). The throttle comes down at its normal rate. After 30 s of calm
  water the reduction goes back slowly (+5 % every 10 s). In AUTO, slamming
  also counts as rough water (the boat slows its target speed, chapter 7).
  OVERRIDE (only with the joystick on board, never the remote driver):
  "kick-down" - ease the throttle off (below 85 %), then push it to full
  and hold 1 s. The reduction is lifted (warning beep, "OVERRIDE" shown)
  until you go below the reduced value again. The power limit still applies.
  Staying at full throttle all the time never overrides.
  The limit: parameter slam_limit_g (1-8 g); the RED action: parameter
  slam_red_reset (0 = STEP, 1 = LIMIT_RESET). The captain proposes, the
  driver confirms on the driver screen (part I).
  Sensor not working: "slamming sensor lost" warning, no reduction, the
  boat drives on normally.
  In the log: every impact as a SLAM event (peak, level, rate, reduction).

I. TWO MONITORS: CAPTAIN SCREEN AND DRIVER SCREEN
  The normal ground-station window is the CAPTAIN screen (everything). The
  button "Driver screen" (top bar) opens the DRIVER screen - drag it to the
  second monitor (or the driver's PC monitor) and make it full size:
    top        rear cameras as mirrors (REAR-LEFT left, REAR-RIGHT right,
               flipped like a mirror), MODE, alarms, internet channel
               (STARLINK in yellow), latency, REC, joystick / remote status
    middle     the FRONT camera big (FRONT-2 by itself if FRONT-1 is lost;
               VIDEO FROZEN within 1 s; "NO FRONT CAMERA" warning while
               driving remotely without a live front camera)
    left       throttle bar: green = throttle now, red line = power limit,
               shaded "SLAM" part = cut by the slamming reduction
    right      speed, slamming graph (bars around the running average, red
               dashed line = limit; click it for absolute g), small map
    bottom     compass tape (heading in the middle, blue mark = target
               heading in HDG LOCK / AUTO), big SAVE button
  CAPTAIN ACTIONS THAT CHANGE THE DRIVING (mode, AUTO start / pause /
  resume / skip, heading +-1/10, sea state, training, parameters such as
  slam_limit_g, power-limit code) are only sent when the driver presses
  ACCEPT on the driver screen. THE GATEWAY ENFORCES THIS (not only the
  screen): it holds the action and asks the driver screen itself.
    no driver screen open           REFUSED "driver screen not open"
    driver presses REJECT           REFUSED "rejected by the driver"
    no answer within 10 s           REFUSED "no answer from the driver"
    driver screen closed / crashed  REFUSED "driver screen lost"
                                    (the driver screen tells the gateway
                                    every second that it is open)
  STANDBY, "Lower now", alarm ack and HELM never wait.
  SINGLE-OPERATOR MODE (one person alone at the station): button "Single
  operator" on the captain screen -> a warning -> ON. A purple banner on
  both screens shows it; the gateway logs it. Every driving action then
  needs YOUR confirmation in a small window (SEND / Cancel, 10 s). It
  switches OFF by itself when this station disconnects (also after a
  crash); press the button again to switch it off.
  The USB laptop on the boat (no gateway) is the service link: there the
  driver window asks when it is open, otherwise the action goes directly.
  Both window places (monitor, size) are remembered (gs_layout.json) and
  come back at the next start. F12 (or Ctrl+Tab) swaps the two windows
  between the monitors.


J. AIS: OTHER SHIPS (RECEIVE ONLY)
  The Pi listens to AIS (no transponder: other ships do NOT see us on AIS).
  Receiver: a dAISy HAT on the Pi (or a USB AIS receiver) with its own
  VHF/AIS antenna. The AURIX never sees AIS - the Pi decodes it:
    * position reports Class A (big ships) and Class B (small craft),
    * name, size, type, destination (static data).
  Each ship shows its age; with no new position it becomes STALE after
  3 min (Class A) / 6 min (Class B) and disappears after 15 min. Between
  reports the position is predicted from speed and course. Wrong data is
  ignored (bad checksum, impossible jumps).
  AIS RECEIVER SILENT (alarm, warning only): no AIS message for 5 minutes
  while at sea (moving or in a driving mode). Check the antenna cable and
  the receiver. It never changes the mode or the power limit.
  ONLINE AIS (AISHub, wider area): OFF by default; only on 4G / RF, NEVER
  on STARLINK. Ships seen by our own receiver keep our data when it is
  newer.
  SECOND GPS: if the AIS device has its own GPS (a future Class B
  transponder, or $GPRMC from the receiver), the Pi can send it to the
  AURIX as a second, independent GPS: setting ais.second_gps = true on the
  Pi AND parameter gps2_check_m (e.g. 30) on the boat. A main GPS more than
  that far from the second one is not trusted (spoofing). Tested: drags of
  0.2 m/s and slower are NOT found by the other checks within 10 minutes,
  the second GPS finds them at 30 m. Both OFF by default.
  AIS DOES NOT SHOW small boats, jet skis, swimmers, kayaks or anything
  without a transponder. The lookout on board and the cameras stay essential.

K. DEPTH CHARTS AND SEA MARKS (OFFLINE)
  NOT FOR NAVIGATION - free data, may be inaccurate near the coast. This
  note is always on the map. Use the official charts and your eyes.
  Area: Saronic Gulf, the Attica coast around Sounion, the South Euboean
  Gulf, Kea / Makronisos, with a margin (charts\areas.json - add more areas
  there). Depth: EMODnet Bathymetry (about 115 m grid, depth below the
  lowest tide), sea marks (buoys, beacons, lights, harbours): OpenSeaMap.
  Gaps can be filled from a GEBCO grid. Their names are shown on the map
  (the licences require it).
  MAKE THE CHARTS ONCE (needs internet, about 10 minutes):
       C:\msys64\ucrt64\bin\python.exe tools\chartprep.py
  -> charts\attica\ (depth.bin, contours.json, seamarks.json, area.json).
  Copy that folder to the Pi too (gateway\README.md section 18): the Pi uses
  it for the shallow-water checks. After that the map works with NO
  internet.
  Map tab: Depth (shading: dark = shallow, white = deep, sand = land),
  Contours (2, 5, 10, 20, 50, 100 m), Sea marks, AIS ships - each on / off;
  "depth shading" = how strong the colours are. Zoom out up to 400 m per
  pixel. The driver screen's small map shows the same, 3 km wide.
  On the map, everywhere the data has no depth (land, harbours, very close
  to the coast) counts as SHALLOW for every check (part L).

L. SHALLOW WATER
  Limit = the larger of 3.0 m and (draft + margin). SET THEM ON THE PI
  (/etc/trygons/gateway.json "shallow"): draft_m = from the water line to
  the lowest point of the outboard with the leg DOWN (measure it!), margin_m
  = how much water you want under it (1 m), shallow_m = at least this (3 m).
  The ground station shows the limit (Program tab profile, red line).
  AUTO PROGRAMS (Program tab):
    * "Check depth": every leg must stay over water deeper than the limit
      and not pass closer than 50 m to shallower water. A bad leg is shown:
      the message gives the leg and the position, a red X on the map, the
      depth profile (red = too shallow).
    * Upload and AUTO start / resume through the gateway are REFUSED the same
      way by the Pi ("shallow water on the route: leg ... at lat lon"), also
      the leg from the boat to the waypoint at AUTO start. Without charts on
      the Pi AUTO is refused ("no depth charts").
  WHILE DRIVING (any mode): if the boat will be over shallow water within
  the next 30 s (at least 200 m ahead) -> "SHALLOW WATER AHEAD" on both
  screens. In AUTO the boat also slows to 4 kn and the SHALLOW WATER alarm
  sounds. In MANUAL / HDG LOCK / REMOTE it is a warning only: you steer.
  Every collision-avoidance route (part M) passes the same depth check.
  The charts are free data and NOT FOR NAVIGATION: near the coast, in
  harbours and where there is no data, "no data" counts as shallow.
  How AUTO is slowed: the Pi sends a "navigation request" twice a second
  (speed cap, avoidance heading, alarms) that the boat applies only in AUTO.
  If the Pi goes quiet in the middle of such a request, the boat holds its
  heading, slows to 4 kn (parameter nav_lost_kn) and sounds COLLISION RISK -
  DRIVER DECISION. Joystick and STANDBY always win.

M. COLLISION AVOIDANCE (AIS SHIPS)
  AIS DOES NOT SHOW small boats, jet skis, swimmers, kayaks, divers or
  anything without a transponder, and a ship's AIS can be wrong, late or
  switched off. Collision avoidance helps with BIG ships only. KEEP A
  LOOKOUT. A radar reflector on the boat helps big ships see YOU.
  The Pi computes for every AIS ship the CPA (how close it will pass) and
  the TCPA (in how many minutes):
    WARNING  CPA under 0.5 nm within 10 min   (yellow on the maps)
    DANGER   CPA under 0.25 nm within 6 min   (red on the maps + the
             driver screen; alarm COLLISION RISK, video SAVE)
  (Pi settings /etc/trygons/gateway.json "avoid": warn_nm, warn_min,
  danger_nm, danger_min, safe_nm, clear_nm, min_kn ...)
  WHAT HAPPENS IN EACH MODE:
    AUTO       automatic, step by step, already at the WARNING level (early,
               while there is still room):
               1. slow down (half speed, at least 4 kn) and re-check after
                  20 s;
               2. still too close -> a route that passes ASTERN of the ship
                  (starboard turns first, then port; it never crosses ahead
                  of a ship's bow, keeps 0.5 nm, and passes the depth check
                  of part L). The route is drawn on both maps.
               3. clear (going back is safe) -> the boat rejoins its leg.
               Every decision is written to the Pi's audit log.
    HDG LOCK   at the WARNING level too: the same route as a PROPOSAL on the
               driver screen ("Steer
               074 and slow to 4 kn?") - ACCEPT changes the locked heading,
               REJECT keeps it (no new proposal for 60 s, the alarm stays).
               When clear: "Back to heading 344?" (ACCEPT / REJECT). The
               throttle stays with you. Only the driver screen (or the
               captain in SINGLE-OPERATOR mode) can answer.
    MANUAL / REMOTE MANUAL   alarm only: you steer.
    STANDBY / TRAINING       nothing.
  COLLISION RISK - DRIVER DECISION: the situation can't be solved safely by
  the Pi (two or more dangerous ships, a ship that is turning, old / stale
  AIS data, no safe route): in AUTO the boat slows to 4 kn and KEEPS ITS
  COURSE (never an unchecked route). YOU decide: take the joystick.
  The boat only applies what the Pi asks in AUTO (or after your ACCEPT in
  HDG LOCK), and only within all its own rules (power limit, joystick
  wins, STANDBY wins). If the Pi goes silent during an avoidance, the boat
  holds its heading, slows to 4 kn and sounds DRIVER DECISION.
  Collision and shallow-water alarms do NOT lower the power limit (slowing
  down is done by the speed request itself).
  Captain screen, tab "AIS": the ship list (name, distance, bearing, CPA,
  TCPA, age), click a ship for its details.

N. OBSTACLE DETECTION WITH THE FRONT CAMERA (eWaSR, AI)
  The Pi looks at the front camera (FRONT-1, FRONT-2 after a switch-over)
  with a small AI model (eWaSR) that colours every part of the picture as
  WATER, SKY or OBSTACLE. Things sitting on the water (boats, buoys,
  swimmers, rocks) become obstacles with a bearing and a ROUGH distance.
  IT NEVER STEERS THE BOAT AND NEVER GIVES MORE THROTTLE. It does not see
  everything (night, fog, glare, small things far away): keep a lookout.
  Licence: model and code Apache-2.0, test pictures MaSTr1325 CC BY 4.0 -
  both allowed for this project (gateway\vision\README.md).
  STAGES (captain screen, Cameras tab; every change is logged):
    1 overlay + log    (ON)  colours over the front camera on the driver
                             screen, boxes with bearing + "~120 m (rough)",
                             orange sectors on the maps, a log file
    2 alarm + SAVE     (ON)  an obstacle in the path ahead (only while
                             driving, not moored in STANDBY): alarm
                             OBSTACLE AHEAD + video SAVE. No effect on the
                             boat.
    3 slows AUTO       (OFF) AUTO slows to 3 kn (idle when nearer than
                             40 m); HDG LOCK: "slow down" on the driver
                             screen (the throttle stays yours); MANUAL /
                             REMOTE: alarm only. Switch it on ONLY after
                             sea trials; the driver screen must ACCEPT it.
  An obstacle must be seen in 3 pictures in a row before it counts (wakes,
  foam and glare flicker and are filtered). The bottom of the picture (own
  bow, own wake) is ignored.
  DRIVER SCREEN: "VISION ACTIVE 2.0 fps" in the top line; buttons "overlay
  ON/OFF" and "opacity" under the small map; "CLEAR SLOWDOWN" while a STAGE 3
  slowdown is active.
  STATUS (a notice, never an alarm, never a mode change):
    ACTIVE     working
    PAUSED     the Pi's main jobs need the CPU, or the Pi is hot / throttling
    DEGRADED   too slow (below 1 picture / s) or the camera gives no pictures
    OFFLINE    switched off, model missing, crashed (it restarts by itself)
  If vision stops working while it slows AUTO down, the slowdown STAYS until
  the driver presses CLEAR SLOWDOWN (it is never released by itself).
  The Pi needs its ACTIVE COOLER (PARTS.md). Setup and the model file:
  gateway\vision\README.md. Your own recordings can be tested on the PC:
     tools\bin\vision-python\python.exe gateway\vision\evaluate.py FILE.ts
  -> test_results\vision_eval\report.md (speed, detections, pictures).
  Samples for an own Saronic dataset (picture + mask) can be switched on
  (vision.samples on the Pi); they use at most 500 MB.

10. THE POWER LIMIT
-------------------------------------------------------------------------------
  * After EVERY power-up or reset: 30 % forward, 5 % reverse (of the full
    throttle travel). Never saved.
  * Raise, one step at a time (30 -> 50 -> 75 -> 100 %; reverse 5 -> 10 -> 15):
      1. "Raise fwd" (or "Raise rev") in the ground station,
      2. type the 4-digit code the window shows, "Send code",
      3. press CONFIRM on the joystick within 10 s (stick centred).
    Each step needs the whole sequence again. Wrong / old code: refused.
  * It drops back to 30 / 5 AT ONCE on: "Lower now", TAKE or a stick
    takeover, the STANDBY button, ANY alarm (incl. PC link lost, GPS lost,
    compass / joystick / gear fault), entering TRAINING, and after 2 min
    below 3 kn. The throttle then comes down at its normal rate (no sudden
    cut), but it can never go above the new limit.
  * In AUTO the leg speed is limited by it; the window shows "SPEED LIMITED
    BY POWER LIMIT".
  * Enforced in the lowest layer: app/servo.c, the only code that drives
    the throttle servo. The CPU1 monitor checks it again.

11. ALARMS
-------------------------------------------------------------------------------
  COMPASS LOST, GPS LOST, GPS SUSPECT (spoof flag, jump, speed, course,
  slow drag, second GPS, or a fix with impossible numbers - NaN, latitude
  beyond 90, ...), DEAD RECKONING LIMIT,
  ARRIVAL UNCERTAIN, ARRIVED, GEAR FAULT, TRAINING,
  JOYSTICK FAULT, JOYSTICK NOT CENTRED, JOYSTICK TOOK CONTROL,
  PC LINK LOST
  NOT NEUTRAL AT START   outputs not armed: gear not in neutral / stick held
  SAFETY MONITOR TRIPPED CPU1 forced idle + neutral (see chapter 12)
  CONTROL LOOP OVERRUN   a control cycle took longer than 50 ms
  LOG FAILURE            SD card missing / full / failing (control goes on)
  GATEWAY LOST           the Raspberry Pi is silent for 3 s (no mode change)
  SHALLOW WATER          AUTO: shallow water ahead (charts); the boat slows to
                         4 kn (part L)
  COLLISION RISK         an AIS ship will pass closer than 0.25 nm within
                         6 min (part M); AUTO avoids it, HDG LOCK proposes
  OBSTACLE AHEAD         the front camera sees an obstacle in the path (part N,
                         STAGE 2 / 3); a warning - only STAGE 3 slows AUTO
  COLLISION RISK - DRIVER DECISION  the Pi can't solve it safely (or went
                         silent during an avoidance): slow, keep course - YOU
                         decide (part M)
  AIS RECEIVER SILENT    no AIS message for 5 min at sea: antenna / receiver
                         (warning only, part J)
  SLAMMING               an impact harder than slam_limit_g: throttle reduced
                         one step, video SAVE; the power limit stays (only
                         with slam_red_reset = 1 it drops to 30 %) (part H)
  GATEWAY STORAGE        the Pi's USB SSD is missing / failing, or STORAGE FULL
                         (no mode change; SAVE refused while full)
  REMOTE LINK LOST       the remote station holding HELM disappeared; HELM
                         goes back to nobody (no mode change)
  CHANNEL FALLBACK       the internet channel you chose (MANUAL) failed; the
                         gateway uses the next working one (no mode change)
  REMOTE DRIVING LINK LOST  remote joystick data too old / missing: idle,
                         neutral, gyro heading hold; STANDBY after 5 s

  Every new alarm drops the power limit to 30 / 5 and starts a black-box
  file (except the navigation warnings SHALLOW WATER, COLLISION RISK, DRIVER
  DECISION, OBSTACLE AHEAD and AIS RECEIVER SILENT: they never change the
  power limit). Acknowledge: STANDBY button in STANDBY, or "ACK ALARM".

12. SAFETY RULES BUILT INTO THE SOFTWARE
-------------------------------------------------------------------------------
  * Gear changes only at idle: idle -> wait -> neutral -> wait -> gear.
  * Every fault / STANDBY: idle + neutral FIRST, then steering off. In
    STANDBY the throttle closes at 100 %/s (idle within 1 s); until idle +
    neutral the onboard stick (from MANUAL) or the gyro (from REMOTE, or a
    joystick fault) keeps steering.
    Compass lost while moving (AUTO / TRAINING): gyro steering until
    stopped (or outboard to centre if the gyro is gone too). In HDG LOCK:
    gyro hold, the throttle stays with you; STANDBY once you have stopped.
    In MANUAL: alarm only.
  * Throttle rate limits; reverse limited; the power limit (chapter 10).
  * The joystick always wins; the STANDBY button always wins.
  * NEUTRAL-START INTERLOCK: after power-up the outputs only arm when the
    throttle is idle, neutral is confirmed (neutral switch if fitted) and
    the stick is centred. Until then: STANDBY only, safety relay open,
    alarm after 3 s.
  * WATCHDOGS on all three cores (100 ms on core 0). A stuck loop resets
    the chip: everything starts again in STANDBY at 30 %.
  * CPU1 SAFETY MONITOR: checks every 1 ms, on its own: throttle above the
    power limit, gear moving with the throttle open, core 0 silent for
    200 ms. Then it forces idle + neutral + steering off + alarm + safety
    relay open, and core 0 can't undo it until a reset. Reaction in the
    simulator: 10-20 ms (one check), 220 ms for a frozen core 0.
  * Heading hold pauses (outboard held still) when there is no propulsion,
    so the angle estimate can't drift while you are stopped.
  * Logging can never block control (chapter 13).

13. LOGGING (SD CARD) AND THE LOG TOOLS
-------------------------------------------------------------------------------
WHAT IS LOGGED: 20 times a second 86 values (mode, all sensors raw and
filtered, GPS with satellites and spoof flag, PID terms, outboard estimate,
throttle after every limit stage, gear, power limit, navigation, position
estimate + uncertainty, current, joystick, buttons, CPU times, supply
voltage) and every event with its time (mode changes and refused requests,
every PC command with its answer, every button, alarms on/off, power-limit
changes and raise attempts, training, GPS lost / suspect / recovered,
faults, resets with the reason, program steps, config changes).

FILES on the card (FAT32, read them with a card reader):
  Bbbbbb_fff_YYYYMMDD-HHMM.TLG   b = boot number, f = file number; a new
                                 file every 10 min (date once GPS is fixed)
  BBbbbbb_nnn.TLG                black box: the 60 s before an alarm /
                                 fault and the 30 s after
Every file starts with the description of the fields and the full config,
so every file can be read on its own. A power cut loses at most ~2 s.

THE TOOLS (in groundstation\, use C:\msys64\ucrt64\bin\python.exe):
    python logview.py FILE.TLG          plots, map, events; click an event
                                        to jump there
    python log2csv.py FILE.TLG          -> CSV for Excel (all fields)
    python log2csv.py FILE.TLG -f heading,target,thr_out --events
    python log2csv.py FILE.TLG --list   the field names
    python tlgreplay.py FILE.TLG        replay the drive in the simulator
The ground station saves its own copy of the telemetry in the same format
(groundstation\logs\log_*.TLG).

     [ ] Calibrate the throttle servo endpoints (idle / full pulse) and the

     [ ] Measure the outboard (TRAINING), tune the steering on the water.
     [ ] Try the power-limit steps and the low-speed drop at sea.

D) KNOWN LIMITATIONS / JUDGEMENT CALLS
     * After a power-limit drop the throttle comes down at 40 %/s (not a
       sudden cut), which takes up to ~1.8 s from 100 % to 30 %.
     * The STANDBY button works even with the stick held (the stick is
       then ignored until centred). The PC can't leave MANUAL at all.
     * A STOP waypoint only chirps; the "ARRIVED" alarm is for the end.
     * The PC may acknowledge alarms in any mode (the panel button only in
       STANDBY).
     * A normally-open STANDBY button can't be pressed if its wire breaks;
       a normally-closed button with a line check would catch that.
     * Settings changed from the PC are lost at power-off.
     * A new program can't be uploaded while AUTO runs.
     * Joystick hand-back in a running AUTO goes to STANDBY (resume = PC +
       CONFIRM).
     * USB lever: hand-back (and HDG LOCK from MANUAL) needs the lever in
       the neutral zone, so the engine is at idle at the hand-back.
     * USB lever: CONFIRM only needs the stick centred, not the lever.
     * USB joystick fault while driving: the stick that steered is gone,
       so the gyro holds the course while the throttle comes down at the
       STANDBY rate, then neutral, then steering off - same as a broken
       wire on the analog stick.
     * While mapping buttons, the old map still works (TAKE takes over).
     * Core 2 RAM and the LMU blocks are 81-84 % full (the black box). Each
       new byte in the 20 Hz log record costs 1.2 KB of black box: the slot
       is 184 B (182 used) - a bigger record needs LOG_BB_SLOT raised and
       mapreport.py checked (or a shorter black box).

19. TESTING (THE ACCEPTANCE TEST)
-------------------------------------------------------------------------------
Besides the normal tests (chapter 4 and tools\check.sh before every commit)
there is a big acceptance test that checks the WHOLE system. Run it before
sea trials and after big changes:

    tests\acceptance\RUN_ACCEPTANCE.bat          quick: about 10-15 minutes
    tests\acceptance\RUN_ACCEPTANCE.bat full     everything: several hours

(or: C:\msys64\ucrt64\bin\python.exe tests\acceptance\run_acceptance.py quick)
Extra install for the coverage part only:
    pacman -S mingw-w64-ucrt-x86_64-python-coverage

WHAT IT DOES
  fresh build        clones the project from GitHub into an empty folder and
                     builds / tests it there, following only this manual -
                     finds files or steps that only exist on this PC
  fault storm        2000 (quick: 200) random "bad days" of 5-30 min each in
                     the simulator, much faster than real time: sensor
                     failures, broken frames on every link, random joystick
                     and buttons, random PC commands, resets, a frozen core 0
                     ... After EVERY control step 21 safety rules (I1..I21,
                     e.g. "STANDBY always wins") are checked. It first proves
                     that the checks work (it plants 3 violations and they must
                     be caught).
  time wrap          the boat's millisecond clock runs over 49.7 days
  soak               24 h of boat time (AURIX, with logging) + a real-time
                     run of the gateway with cameras, recording, vision, AIS,
                     sync: memory, files, sockets, timing over time (a leak
                     shows as a growing line)
  day at sea         one long mission through everything (two parts: the
                     AURIX with its faults in simulated time, and the whole
                     system in real time) - a timeline table
  gateway storms     random traffic / channels / storage / vision / stations
                     against the gateway's own rules (I14-I17, I20, I21)
  coverage           which code the tests run at all (full only)

HOW TO READ THE RESULT
  test_results\acceptance_summary.txt: one line per part, PASS / FAIL, and
  the name of its log file next to it. In a log:
    PASS / FAIL lines   one per rule or step; FAIL = look closer
    "seed N"            a random run can be repeated exactly:
                          test_results\storm.exe --replay N
                        prints every event of that run; "minimal N events"
                        = the shortest list of events that still fails
    worst reaction      e.g. "worst 2.88 s" for STANDBY = the slowest the boat
                        took (idle + neutral) in all the runs
  A FAIL is not always a bug in the boat: it can be the test itself. The last
  full result, every finding and what to fix first: TEST_REPORT.md (project
  folder). The large outputs (logs, coverage pages, soak data) stay in
  test_results\ - not in git; delete it any time.
  What the PC can't test (real board timing, the Pi's speed, the sensors,
  the sea): TEST_REPORT.md section 4.
